DAY 2 · 手把手教程

结构化输出 / JSON mode

搞懂「能解析」和「字段对」是两件事，分清三种强度，并能给自己任何一个任务写出可验证的输出契约。

学习 60 分钟 + 练习 45 分钟 网页版为主 · 代码侧选做 含 4 个练习 · 附参考答案 不需要 API key 也能做完
今日一句话：JSON mode 保证「能解析」，Structured Outputs 保证「字段对」。 今天所有内容，都是为了让这句话从背下来变成真正理解。

开场先看一次"成功的失败"

这是初学者最容易掉进去的坑：输出看起来是 JSON，其实已经废了。

你让模型从一段新闻里抽取信息，要求输出 JSON，字段是 time / location / persons / event_type。模型返回了这个：

好的，根据您提供的新闻内容，我为您提取了以下信息：
{
  "时间": "2026年10月14日",
  "地点": "成都",
  "涉及人员": ["张某", "李某"],
  "event_type": "事故"
}

↑ 这是合法的 JSON，能被 json.loads 解析。但你的程序要的是 time，拿到的是 时间——取值为 None，下游直接崩。

✋ 停 30 秒

这份输出里，有几处不满足你的要求？把它们找出来再往下读。

参考答案：有 4 处问题

① 前面夹带了废话。"好的，根据您提供的新闻内容……"——这行不是 JSON 的一部分，直接导致整个字符串解析失败。（严格说这个例子里连"能解析"都没做到。）

② 字段名被翻译了。你要 time，它给 时间；location 变成 地点，persons 变成 涉及人员。

③ 字段名不统一。前三个翻成中文，event_type 却还是英文——模型自己都没拿定主意。

④ 枚举值不可控。你规定了事件类型只能是 事故/会议/发布 之一，它给了"事故"，这次蒙对了，但下次可能给"意外事故"。

关键认知：这四个问题里，只有①是"能不能解析"的问题，②③④全是"字段对不对"的问题。而这两类问题，需要两种不同强度的手段来解决。这就是今天的核心。

01三种强度：从"看运气"到"不可能错"

把输出约束想象成三档开关。档位越高，模型"做错的空间"越小。

第 1 档 纯文本 + 描述 Prompt only

什么都不保证。你只在提示词里说"输出 JSON，字段有……"，模型照做算运气好。

# 你写的
请从新闻中提取时间和地点，用 JSON 输出。

# 模型可能返回
好的：{"时间": "10月14日"}   ← 带废话 + 字段名被改
保证什么什么都不保证
失败率行业经验值：纯提示词约束的 JSON，约 15–25% 的返回无法直接解析
什么时候够用你自己肉眼看输出、不需要程序处理
第 2 档 JSON mode response_format: json_object

只保证"能解析"。输出一定是语法合法的 JSON，但字段可能缺、可能改名、枚举可能非法。

# 代码侧写法
response_format={"type": "json_object"}

# 保证：一定是合法 JSON，不会有前后废话
# 不保证：字段名对不对、字段在不在、枚举合不合法
{"时间": "10月14日"}   ← 合法，但字段名错了，它照样返回
这是今天第一个要记住的事实：JSON mode 的合同范围比大多数人以为的窄得多。它只管"括号配不配、引号对不对"，完全不管里面装的是什么。
第 3 档 Structured Outputs response_format: json_schema, strict: true

保证"字段对"。在生成层面屏蔽非法 token——模型不是"不太可能写错"，而是"写不出来"。

# 代码侧写法
response_format={
  "type": "json_schema",
  "json_schema": {"name": "news", "schema": {...}, "strict": True}
}

# 官方评测：复杂 schema 遵循率 100%
# 原理：受限解码 —— 每一步生成时，把所有会让输出违反 schema 的
#       token 直接屏蔽掉，模型根本选不到它们
打个比方：JSON mode 是"考完卷子再批改"，Structured Outputs 是"把答题卡做成填空题，错误答案压根填不进去"。

三档横向对比

维度纯文本JSON modeStructured Outputs
保证无合法 JSON完全符合 schema
字段缺失会会不会
字段名被改会会不会
枚举出非法值会会不会
下游还要校验吗必须必须建议仍校验（防业务级错误）
官方评测符合率约 75–85% 可解析低于 Structured Outputs100%

注意最后一列仍写着"建议校验"：Structured Outputs 保证的是形状对，不是内容对。字段都有、类型都对，但"地点"填了个错误的地方——它管不了。内容正确性要靠别的方法（这属于 Day 4 的范畴）。

02网页版：你能做到的最强约束是第 2 档

先说清楚一个事实，免得你白费力气。

重要前提 在 ChatGPT / DeepSeek / 豆包这类网页版对话框里，你无法开启真正的 Structured Outputs——那是 API 侧的参数。网页版能达到的最强水平是第 2 档：通过把提示词写得足够死，让模型"大概率"输出正确字段。

所以网页版的策略是：用第 1 档的工具，逼近第 2 档的效果，并且自己做好校验。

网页版"逼近第 2 档"的四条写法

① 字段名用英文，并明确禁止翻译

✗ 提取：时间、地点、人物
✓ 字段名必须使用英文：time、location、persons。不得翻译或改写字段名。

② 给出完整结构，而不是描述结构

✗ 请以 JSON 格式输出时间和地点
✓ 严格按以下结构输出：
{
  "time": "字符串，YYYY-MM-DD 格式",
  "location": "字符串，城市名",
  "persons": ["字符串数组，人物姓名"]
}

差别在于：前者是"描述"，后者是"样板"。模型模仿样板的能力远强于理解描述。

③ 明确"只输出 JSON，不要任何前后文字"

✓ 只输出 JSON 本身。不要输出任何解释、前缀、后缀、或 markdown 代码块标记。
   第一个字符必须是 {，最后一个字符必须是 }。

"第一个字符必须是 {" 这句特别有效——它把要求变成了可检查的硬指标。

④ 枚举值列死，并说明越界怎么办

✓ event_type 只能是以下之一："事故"、"会议"、"发布"、"其他"。
   若无法确定，填 "其他"，不得自行创造新值。

"不得自行创造新值" + "给出兜底选项"，这两句配套使用——只禁止不给出路，模型还是会编。

网页版完整示例（可直接复制使用）

# 任务
从下面这段新闻中提取信息。

# 输出格式
只输出 JSON 本身，不要任何解释文字，不要用 markdown 代码块包裹。
第一个字符必须是 {，最后一个字符必须是 }。
严格使用以下结构（字段名不得翻译、改名、增删）：

{
  "time": "事件发生日期，YYYY-MM-DD 格式；若文中未提及则填 null",
  "location": "发生城市，不带省名；若未提及则填 null",
  "persons": ["文中出现的人物姓名，若无则填空数组"],
  "event_type": "只能是 事故/会议/发布/其他 之一"
}

# 新闻
【此处粘贴新闻正文】

↑ 这四段正好对应你 Day 1 学的五层：任务层 / 格式层 / 约束层，一气呵成。格式层写死了，就是结构化输出。

✋ 现在动手：网页版对比实验（20 分钟）

找一段新闻（或任何含多个信息的文本），用同一个抽取任务跑两遍：

写法 A（弱）："请从这段新闻里提取时间、地点、人物、事件类型。"
写法 B（强）：用上面那个完整示例。

各跑 3 次，共 6 次。统计：能直接解析的次数 / 字段名完全正确的次数。

你会看到 A 大概率夹带废话或被翻译字段名，B 明显更稳——但B 也可能偶尔翻车。记住这个"偶尔"，它就是第 2 档的天花板。

03代码侧：第 3 档是怎么做到的（了解即可）

没有 API key 也能看懂这一节。目标是"知道有这条路"，不是今天必须跑通。

原理一句话：受限解码

Structured Outputs 不是"生成完再检查"，而是在生成的每一步就屏蔽掉非法选项。

具体来说：模型每生成一个 token 前，系统会算出"哪些 token 会让输出违反 schema"，然后把它们直接从候选里划掉。所以如果 event_type 定义成只能是「事故/会议/发布」，模型在结构上就不可能在这个位置输出"意外"——不是"被劝阻"，是"选不到"。

这也解释了为什么它快：不需要重试。第 1、2 档遇到错格式要重跑一遍，而重跑的成本远高于 schema 校验那点开销。

Python 最小示例

from pydantic import BaseModel
from openai import OpenAI

client = OpenAI()

# 1. 用类定义结构（比手写 JSON Schema 省事）
class NewsExtraction(BaseModel):
    time: str          # 事件发生日期
    location: str
    persons: list[str]
    event_type: str    # 事故 / 会议 / 发布

# 2. 发起请求，让 SDK 自动解析成对象
completion = client.chat.completions.parse(
    model="gpt-4o-2024-08-06",
    messages=[
        {"role": "system", "content": "从新闻中提取信息。"},
        {"role": "user", "content": news_text},
    ],
    response_format=NewsExtraction,
)

result = completion.choices[0].message.parsed
print(result.event_type)   # 直接是对象属性，不用 json.loads

↑ .parse() 这个方法是关键：它把"定义结构 → 转 schema → 解析返回"三步都包了。

第 3 档的代价：只支持 schema 子集

100% 符合率是有条件的。超出下面这些边界，要么报错，要么静默降级：

限制具体是什么 / 怎么绕
嵌套上限约 5 层。树形数据别嵌套，改成扁平列表 + 父 ID 引用
字段必须全 requiredstrict 模式下不能"可选"。真要可选，把类型写成允许 null（如 str | None），而不是省略这个字段
部分关键字不支持minLength / maxLength 等字符串约束不支持——想限制长度，写在字段描述里让模型照做，或在代码里二次校验
跨字段逻辑管不了"如果 A 成立则 B 必须有值"这类，schema 表达不了，只能靠代码校验
模型白名单并非所有模型都支持 strict。老模型、部分开源模型只到 JSON mode
首次请求有延迟新 schema 第一次请求会编译，之后缓存复用
还有一条容易忽略：模型可以拒绝请求。此时返回的是 refusal 而不是 JSON。代码里要判断这个状态——否则你会拿到一个 None 然后困惑半天。
选做练习（有 API key 才做，限时 45 分钟） ① 跑通一次 json_object；② 跑通一次 json_schema + strict；③ 故意写错一次 schema，看报错长什么样。
第③步最有价值——记住那个报错的样子，以后排查能省半小时。
没有 key 就跳过，读一遍文档、抄一遍代码即可。别在装环境上调超过 45 分钟，那是时间黑洞，今天的重点是概念不是工程。

04怎么写好一个 schema

这是今天真正要练的手艺——不管在网页版还是代码侧，都用得上。

四条规则

1

字段名：简短、英文、稳定

用 time 不用 事件发生的具体时间；用 event_type 不用 type（太泛）。 字段名会被程序引用，一旦定了别轻易改。

2

给每个字段写一句"人话描述"

别指望字段名自解释。写清楚口径：location: 发生城市，不带省名 就比光秃秃的 location 强得多。 描述是给模型看的，字段名是给程序看的，两者都要。

3

能枚举就枚举

分类、状态、类型这类字段，尽量列死可选值。这是把"开放题"变成"选择题"——模型做选择题的可靠性远高于开放题。

4

每个字段都要有"兜底路径"

信息缺失时怎么办？明确写出来：若文中未提及则填 null / 填"其他" / 填空数组。 没有兜底，模型就会编——这是新手最容易漏的一条。

对照：一个字段的三种写法

✗ 差
{"event_type": "string"}

~ 一般
{"event_type": {"type": "string", "description": "事件类型"}}

✓ 好
{"event_type": {
   "type": "string",
   "enum": ["事故", "会议", "发布", "其他"],
   "description": "事件类型。只能是枚举值之一；若无法确定，填 '其他'，不得创造新值"
 }}

从"差"到"好"，加的其实只有两样东西：枚举和兜底。

✋ 动手：三个任务，各写一个 schema（30 分钟，今日重点）

下面三个任务，先自己写，写完再对答案。每个限时 8 分钟——别追求完美，追求能跑通。

任务 1 · 分类：判断一条用户评论的情感倾向，输出标签 + 置信度

任务 2 · 抽取：从一段产品介绍里抽取 产品名 / 价格 / 主要卖点（多值）/ 是否有折扣

任务 3 · 多字段摘要：把一篇长文压成 一句话摘要 / 三个要点 / 目标读者 / 字数

任务 1 参考（分类） 
{
  "sentiment": {
    "type": "string",
    "enum": ["正面", "负面", "中性", "无法判断"],
    "description": "情感倾向。无法确定时填'无法判断'"
  },
  "confidence": {
    "type": "number",
    "description": "置信度，0到1之间的小数，保留两位"
  },
  "reason": {
    "type": "string",
    "description": "判断依据，引用评论中的原话，不超过30字"
  }
}

要点：① 加了"无法判断"兜底；② 置信度写清了范围和精度；③ 加 reason 字段强制模型给出依据——这能显著提高判断质量（属于 Day 4 的思路，先用上没关系）。

任务 2 参考（抽取） 
{
  "product_name": {"type": "string", "description": "产品全称；若未提及填 null"},
  "price": {"type": "number", "description": "价格数字，不含货币符号；若未提及填 null"},
  "currency": {"type": "string", "enum": ["CNY","USD","EUR","其他"], "description": "货币代码"},
  "selling_points": {
    "type": "array",
    "items": {"type": "string"},
    "description": "主要卖点，每条不超过20字，最多5条；无则填空数组"
  },
  "has_discount": {"type": "boolean", "description": "是否有折扣；无法判断填 false"}
}

要点：① 价格和货币拆成两个字段，避免"99元"这种字符串污染数值字段；② 数组给了条数上限；③ 布尔值不能填 null，所以明确"无法判断填 false"。

任务 3 参考（多字段摘要） 
{
  "one_line": {"type": "string", "description": "一句话摘要，不超过50字"},
  "key_points": {
    "type": "array",
    "items": {"type": "string"},
    "description": "三个要点，每条不超过30字；必须恰好3条"
  },
  "target_reader": {"type": "string", "description": "目标读者群体，如'产品经理'"},
  "word_count": {"type": "integer", "description": "原文总字数"}
}

要点：① "恰好 3 条"是硬约束，比"大约三条"有效得多；② 字数限制写在描述里（因为 strict 模式不支持 maxLength）。

写完怎么验证：每个 schema 拿去跑一次，检查两件事—— ① 能不能被 json.loads 解析； ② 字段名和你要的一字不差、字段一个不少。
今日通过标准就是这三个任务 3/3 全过。网页版跑的话，把输出粘到任意 JSON 校验工具里验一下即可。

05三种典型失败与修法

今日通过标准要求"失败清单里有至少 3 条记录"。下面三条是最常见的，你还要加上自己踩到的。

失败一：输出夹带前后废话
现象：返回 好的，以下是提取结果：\n{...}，或整个 JSON 被 ```json ``` 代码块包住。
为什么：模型默认把"先说一句再给结果"当成礼貌/完整。
修法：加硬约束——"只输出 JSON 本身，第一个字符必须是 {，最后一个字符必须是 }，不要用 markdown 代码块包裹"。
根治：用第 2 档 JSON mode 或第 3 档 Structured Outputs，让它在结构上没法夹带。
失败二：字段名被改名或翻译
现象：你要 location，它给 地点；或者 persons 变成 people。
为什么：模型把字段名当成"要表达的意思"而不是"固定的标识符"，尤其在你用中文描述任务时。
修法：提示词里写死——"字段名必须严格使用：time、location、persons。不得翻译、改名、增删字段"。
根治：只有第 3 档能真正杜绝。
失败三：嵌套层级或枚举值不符合要求
现象：要 {"a": {"b": "c"}}，它给 {"a": "c"}；枚举规定"事故/会议"，它给"意外事故"。
为什么：结构复杂时模型会"自作主张简化"；枚举没有兜底选项时它会创造新值。
修法：① 在提示词里贴出完整的目标结构样板（不是描述，是样板）；② 枚举一定要配一个"其他/无法判断"兜底，并写明"不得创造新值"；③ 嵌套超过 5 层就改扁平结构。

06什么时候不该用结构化输出

会判断"不该用"，才算真的懂了。

场景为什么不该用该用什么
答案给人读用户要看的是文章、解释、故事。逼模型吐 JSON，人读起来是灾难直接输出自然文本
需要自由发挥头脑风暴、创意写作。schema 会把可能性框死纯文本，最多给个宽松的段落结构
结构还没想清楚你自己都不知道要哪些字段，写出来的 schema 明天就得推翻先跑几轮自由输出，看模型都给了什么，再归纳成 schema
一次性、只跑一遍写 schema 的时间比手工整理结果还长直接问，肉眼挑
字段间有复杂逻辑schema 表达不了"A 成立则 B 必须有值"这类约束schema 管形状，代码管逻辑校验
一句话判断标准：这份输出的下一个读者是谁？是程序 → 用结构化输出；是人 → 别用。

  • 失败清单里有至少 3 条记录，且第 4、5 条是自己今天踩到的，并验证过修法有效。

最后三道检验题（闭卷）：
① 模型返回了一个合法 JSON，但字段名全被翻译成中文了——这说明当前处在第几档？该怎么修？
② 你想让某个字段"可选"（可以没有），在 strict 模式下该怎么写？
③ 什么情况下你不该用结构化输出？说出两个场景。
三题都答得上来，今天这 60 分钟就没白花。

检验题参考答案

① 处在第 2 档或更低（JSON mode 或纯提示词）。因为"能解析但字段不对"正是第 2 档的典型特征。修法：提示词里写死"字段名不得翻译"；要根治就升级到第 3 档 Structured Outputs。

② strict 模式下所有字段必须 required，不能省略。做法是把类型写成允许 null（Python 里 str | None，JSON Schema 里 {"type": ["string","null"]}），并在描述里说明"无信息时填 null"。

③ 任意两个即可：答案给人读时、需要自由发挥时、结构还没想清楚时、只跑一遍的一次性任务、字段间有复杂逻辑时。
