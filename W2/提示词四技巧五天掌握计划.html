为什么按这个顺序排

顺序知识点排在这个位置的理由
Day 1系统提示词分层它是「坐标系」。没有分层框架，后面三天的练习就没有挂载点——你要分辨一段提示词用了什么技巧，先得知道一段提示词由哪几层构成。先建骨架，再看零件。
Day 2结构化输出 / JSON mode最具体、最容易立刻验证对错（能不能被 json.loads 解析，是客观判据）。先拿一个「有硬性验收」的技巧建立手感。
Day 3Few-shot示例是「给模式」，比 CoT 更基础。而且 Few-shot 与结构化输出经常同时出现，第二天刚练完 schema，正好接着看示例如何辅助定格式。
Day 4Chain-of-thoughtCoT 可与 Few-shot 合体（带推理链的示例 = Few-shot CoT），放在 Few-shot 之后顺理成章；且 CoT 的判断难度最高（要能判断「该不该用」），放在最后学、留一天缓冲。
Day 5混合分辨 + 验收四个技巧混着出现在真实提示词里，只有合练才能真正达到「分辨」。这一天也是补进度和复盘的安全垫。
最重要的一条取舍 如果你只有时间做三件事，做这三件：Day 1 的五层拆解模板、Day 3 的 0/1/3/5-shot 对比实验、Day 5 的拆解卡。代码 API 部分、Day 4 的五题对比，都是可以砍的。理由：你的验收标准是「分辨」，而分辨能力来自对比样本量，不是来自读更多教程。

03每日详细安排

每天按「学习 → 练习 → 测试 → 纠错」四环节走，每格约 2.5 小时有效任务，其余为缓冲。

DAY 1 系统提示词分层 10/14 周三 · 约 3–3.5 小时
核心问题：一段提示词由哪几层构成？为什么分开写比堆在一起好？——这是后面所有「分辨」动作的基础工具。
学习 45′
搞懂五层结构，以及「为什么要分层」
五层：角色与身份（你是谁、服务对象）、任务与目标（要做什么、什么叫做好）、约束与边界（不能做什么、遇到什么情况怎么办）、输出格式（长什么样、字段/结构/长度）、示例与上下文（给样例、给背景资料）。分层的三个好处：可复用（换任务只改任务层）、可调试（出问题能定位到某一层）、可替换（示例层换一批不影响格式层）。
练习 60′
拆解 2 段真实的 system prompt，逐句标注属于哪一层
素材来源：某个公开的 GPTs / 智能体指令全文、开源项目的 prompt 文件、你常用的 AI 产品的系统提示词。用不同颜色或标记把每一句归入五层之一。重点观察两件事：① 有多少句子其实「跨层」（比如一句里既说了角色又说了格式）；② 约束层是不是被放在了最末尾最容易被忽略的位置。
产出 30′
搭出自己的「通用五层模板」
一页纸：五层各写一句占位句 + 每层 3 条可填内容提示。以后写任何提示词都从这个模板出发。这是本周最重要的产出物之一。
测试 30′
闭卷回忆 + 标层准确率自测
① 不看模板，口述五层并说明每层作用，全对才过；② 找一段没拆过的提示词，逐句标层，准确率 ≥ 80% 才过。
纠错 30′
回头改自己上周写的提示词
翻出吴恩达课程里你写过的 2–3 个提示词，按五层重新归类，标出「缺了哪一层」。大概率你会发现：任务层写得很详细，但约束层和输出格式层基本是空的。
今日通过标准
能不看资料说出五层名称与作用；拿到一段陌生提示词能在 10 分钟内完成分层标注，准确率 ≥ 80%；手上有一份自己的五层模板。
产出：五层通用模板（1 页）· 2 段真实提示词的分层标注稿 · 上周旧提示词的「缺层清单」
DAY 2 结构化输出 / JSON mode 10/15 周四 · 约 3–3.5 小时
核心问题：「能解析」和「字段对」是两件事。分清这两种强度，才看得懂别人的提示词在哪个层级上做了约束。
学习 60′
网页版怎么要 JSON，代码侧两种模式差在哪
网页版：直接在提示词里描述字段名、类型、枚举值，并明确「只输出 JSON，不要任何解释性文字」。
代码侧（了解即可）：response_format: {type:"json_object"} 是 JSON mode，只保证输出是合法 JSON，不保证字段存在、不保证枚举值合法；response_format: {type:"json_schema", strict:true} 是 Structured Outputs，用受限解码在 token 层面屏蔽非法路径，官方评测 100% 符合 schema。代价：只支持 JSON Schema 子集（嵌套上限约 5 层、不支持 minLength/maxLength、strict 模式下所有字段必须 required，可选字段用允许 null 表达）。
练习 45′
网页版对比实验：同一抽取任务跑两种写法
任务：从一段中文新闻里抽取 时间 / 地点 / 人物 / 事件类型 四个字段。写法 A 只说「提取这些信息」，写法 B 明确给出 JSON 结构与字段说明并要求只输出 JSON。各跑 3 次（共 6 次），统计「能被直接解析」的比例。你会明显看到 A 经常夹带「以下是提取结果：」这类废话。
选做 45′
代码路径（有 API key 就做，没有就只读文档）
用 OpenAI 兼容接口跑通一次 json_object，再跑通一次 json_schema + strict:true（Python 可用 pydantic 定义结构）。故意写一次错误 schema，看报错长什么样——记住这个报错，以后排查很有用。没有 key 就改为阅读文档 + 抄一遍示例代码，目标只是「知道有这条路径」。
测试 30′
三个不同任务各写一个 schema 并验证
任务类型：分类（输出 标签+置信度）、抽取（多字段）、多字段摘要。每个写清字段名、类型、枚举值，实际跑一次，要求输出可被 json.loads 解析且字段齐全，3/3 通过。
纠错 30′
整理「不遵守格式」的三种典型失败
① 输出前后夹带解释文字；② 字段名被模型自行改名或翻译；③ 嵌套层级 / 枚举值不符合要求。每条写一句触发原因和一句修法，进失败清单。
今日通过标准
能说清 JSON mode 与 Structured Outputs 的区别（一句话版本：一个保证能解析，一个保证字段对）；三个任务的输出 3/3 可被解析且字段齐全；失败清单里有至少 3 条记录。
产出：网页版对比实验记录（6 次结果）· 三个可复用的 schema · 格式失败清单
DAY 3 Few-shot 示例 10/16 周五 · 约 3–3.5 小时
核心问题：示例不是在「教模型正确答案」，而是在「设定一个让它继续下去的模式」。想通这一点，你看别人写的示例就懂它想传达什么了。
学习 45′
示例到底在传达什么 + 数量、选择、顺序的经验规则
示例传达的不只是答案，更是：输出格式、判断粒度（多细算「负面」）、标签词表（用 P1/P2 还是 高/中/低）、边界怎么判、语气。
数量经验值：3 个是默认甜点（覆盖常见 / 边界 / 棘手各一）；5 个适合字段多的结构化输出；8 个以上收益递减，顺序敏感性也变强。
选择规则：多样性优先于数量；格式必须完全一致；分类任务每个标签至少一个例子；示例标错比选错更致命。
顺序规则：存在首因/近因偏差，同类标签不要扎堆排；重要场景至少测 3 种排序。
练习 90′
0 / 1 / 3 / 5-shot 四版本对比实验
选一个真实任务（推荐：客服意图分类，或影评情感 + 理由）。写四个版本的提示词，用同一批 10 条输入分别跑一遍，记录：格式一致性（口径是否统一）、判断一致性（同样输入多次跑是否稳定）、加第几个例子开始稳定。做成一张对比表——这张表就是你日后判断「该给几个例子」的直觉来源。
测试 30′
新任务限时实战
换一个你没写过的任务（如：把用户反馈归类到 5 个产品模块），20 分钟内写出 3-shot 提示词，10 条测试输入中格式与口径一致 ≥ 8 条才算过。
纠错 45′
拆解别人提示词里的示例，判断「这个例子提供了什么」
找 3 段带示例的提示词，对每个示例标注它主要传达的是格式、粒度、词表、边界还是语气；再找出其中的「坏例子」（几个例子长得太像 / 格式前后不一致 / 标错了 / 同类标签扎堆）。这是今天对「分辨」贡献最大的一步。
今日通过标准
能说清「示例 = 设模式」而不是「示例 = 教答案」；给出 0/1/3/5-shot 在自己任务上的对比结论；能一眼指出别人示例集里的三类坏例子。
产出：0/1/3/5-shot 对比表 · 10 条测试集与结果 · 坏例子识别清单
DAY 4 Chain-of-thought 推理链 10/17 周六 · 约 3.5 小时
核心问题：CoT 不是万能增强器。会分辨的人，标志是能判断「这题不该用 CoT」——这才是今天的重点。
学习 60′
三种写法 + 适用边界的硬证据
三种写法：Zero-shot CoT（一句「让我们一步步思考」触发）、Few-shot CoT（给带完整推理链的示例）、手写步骤分解（你自己规定第一步做什么第二步做什么）。
边界证据：一项覆盖 100+ 论文、20 个数据集的 meta 分析显示，CoT 的收益高度集中在数学与符号推理（平均 +12～14 分），在常识、软推理、简单问答上收益接近 0，有时更慢更贵。近年的研究还提示两点：一是推理链越长不等于想得越对；二是推理链不总是忠实的——它不一定反映模型真实的思考过程，别把它当可解释性工具。
练习 90′
同一题跑四种写法，做一张对比表
挑 5 道需要多步推理的题（算术应用题、逻辑题、多条件判断各来几道）。每道题分别用：直接问 / 加「一步步思考」/ 给 2 个带推理链的示例 / 手写固定步骤分解。记录正确率、输出长度、耗时。注意观察：简单题上 CoT 是否只是变长而没变准。
测试 30′
盲测「该不该用 CoT」
给自己 6 道新题（混合：3 道符号/数学类、3 道常识/摘要类），先判断该不该用 CoT 并说明理由，再用选定的方法做。判断准确 ≥ 4/6，做对 ≥ 4/6。
纠错 30′
记录 CoT 的失败模式
① 推理链中途跑偏，最后一步救不回来；② 中间步骤被编造，看起来完整但事实错误；③ 变长变慢但正确率没提升；④ 把推理链当「模型的真实想法」来审计——这是不可靠的。写进失败清单，与 Day 2 的格式失败清单合并。
今日通过标准
能一句话说清 CoT 主要在哪类任务上有效（数学/符号/多步推理），并说出至少两类不该用的场景；盲测判断准确率 ≥ 4/6。
产出：5 题 × 4 写法的对比表 · 6 题判断盲测结果 · 更新后的失败清单
DAY 5 混合分辨 + 结业验收 10/18 周日 · 约 3.5 小时
核心问题：真实提示词四种技巧是混着用的。今天的任务就是——拿到没见过的，切得开、说得出、改得对。
练习 90′
拆解 6–8 段陌生提示词，做「拆解卡」
素材：GitHub 上的 prompt 仓库、公开的智能体指令、别人分享的提示词合集（中英文各来几段）。每张拆解卡写四栏：① 用了哪些技巧（分层 / 结构化 / 示例 / 推理链，可能同时有多个）；② 每一处为什么这样写；③ 好在哪、差在哪；④ 你的改写版本。每张卡限时 10 分钟，逼自己形成直觉而不是慢慢抠。
综合 60′
一个真实任务，四种技巧全用上
推荐任务：把一段长文本（新闻/报告/会议记录）转成指定 JSON 结构的摘要卡片。要求：用五层结构搭骨架；输出格式层写清 schema；给 3 个示例覆盖不同文本类型；对需要判断的字段加推理要求。写完跑通，检查输出能否被解析。
验收 45′
四项结业检查，不看资料完成
① 四个技巧各 30 秒口述：定义 + 适用场景 + 不适用场景；
② 5 段陌生提示词拆解，技巧标注准确率 ≥ 80%；
③ 自己写 4 个提示词（每个以一种技巧为主），隔一小时回看能清楚认出用了什么；
④ 说出每种技巧的 2 个典型失败模式。
复盘 30′
整理成一页《个人提示词检查清单》
往后写任何提示词都对着过一遍：分层齐不齐 → 输出格式写死了没 → 要不要给示例、给几个 → 这题该不该要推理链 → 有没有踩进失败清单里的坑。这份清单是本周唯一的长期资产。
结业通过标准
四项检查全部达标；手上有一份可长期使用的检查清单；能向别人解释这四种技巧的区别（不是只说自己会用）。
产出：6–8 张拆解卡 · 一个四技巧综合提示词 · 个人提示词检查清单（1 页）

04四个技巧的分辨速查

这一节是本计划的核心资产：看到什么信号 → 判断用了什么技巧 → 判断它写得好不好。

系统提示词分层 Layered System Prompt 骨架 · 其他三个技巧的挂载点
一眼认出它的信号
出现 # 或 ## 分节标题；出现「你是……」「你的任务是……」「请遵守以下限制」「按如下格式输出」「举例如下」这几类句子。
  • 角色层：你是资深XX、服务于XX人群
  • 任务层：目标是、要求你、判断标准是
  • 约束层：不要、禁止、必须、如果……则
  • 格式层：字段清单、结构、字数、语气
  • 示例层：Example、例如、输入→输出
写得好 vs 常见毛病
  • 好：五层边界清楚，改一层不动其他层；约束写在靠前位置
  • 好：每层职责单一，一句只说一件事
  • 毛病：所有要求堆成一大段，出问题无法定位
  • 毛病：约束层压在最末尾，长提示词里容易被忽略
  • 毛病：角色层和任务层混写，改任务时误伤角色设定
结构化输出 / JSON mode Structured Output 零件 · 服务于下游程序解析
一眼认出它的信号
出现 schema / 字段名清单 / 「只输出 JSON，不要任何解释」/ response_format / 枚举值限定。
  • 弱约束（JSON mode）：只保证输出是合法 JSON，字段可能缺、枚举可能出非法值
  • 强约束（Structured Outputs）：在生成层面屏蔽非法 token，字段与枚举必然符合 schema
  • 网页版能做的只有「描述结构 + 要求只输出 JSON」，属于弱约束
  • 强约束的代价：只支持 schema 子集（嵌套上限约 5 层、所有字段必填、可选字段用 null 表达）
什么时候用 / 不用
  • 用：下游要程序解析、批量跑、字段固定、需要跨调用一致
  • 不用：答案给人读、需要自由发挥的写作、结构还没想清楚只是在探索
典型失败
  • 输出夹带「好的，以下是结果：」导致解析失败
  • 字段名被模型自行改名或翻译成中文
  • 嵌套层级、枚举值不符合要求
Few-shot 示例 Few-shot Prompting 零件 · 用示范代替描述
一眼认出它的信号
提示词里有 2–5 组「输入 → 输出」的成对示范，常见分隔方式：Example 1/2/3、###、Q: / A:。
  • 关键理解：示例不是在教正确答案，而是在设定模型要延续的模式
  • 它传达的是：格式、判断粒度、标签词表、边界怎么处理、语气
  • 数量：3 个是默认甜点；5 个适合字段多的结构化输出；超过 8 个收益递减
  • 顺序有首因/近因偏差，同类标签不要扎堆
什么时候用 / 不用
  • 用：格式特殊、标签词表是自造的（如 P1/P2/P3）、需要跨几百次调用保持一致、zero-shot 只有六七十分而你要九十分、语气光靠描述定不住
  • 不用：摘要、翻译、明显标签的分类、改写润色、大部分基于清晰上下文的问答——这些 zero-shot 就够
  • 换招：如果是算术/多步推理，直接用 CoT，别堆示例
典型失败
  • 几个例子都长一个样，模型泛化差
  • 示例之间格式不一致（这是最常见的失败原因）
  • 示例本身标错了——比选错例子更致命
  • 同类标签扎堆排列，导致输出偏向某一类
Chain-of-thought 推理链 Chain-of-thought 零件 · 只在特定任务上真的有用
一眼认出它的信号
出现「让我们一步步思考」「先分析再给结论」「请展示你的推理过程」，或示例里带着完整的推导过程。
  • Zero-shot CoT：一句话触发，成本最低
  • Few-shot CoT：示例里带推理链，等于前两个技巧合体
  • 手写步骤分解：你自己规定第一步做什么、第二步做什么，可控性最高
什么时候用 / 不用
  • 用：数学、符号运算、多步逻辑推理、需要跨多条件做判断
  • 不用：常识问答、摘要、简单分类、改写——研究显示这些场景收益接近 0，只是更慢更贵
  • 不用：对延迟敏感、成本敏感、或任务模型已经能直接做对
典型失败
  • 不加区分地对所有任务都用，白白增加成本
  • 推理链很长但答案没更准（写得多不等于想得对）
  • 中间步骤是编造的，看起来完整但事实错误
  • 把推理链当成模型的真实思考过程来审计——它并不总是忠实的
四个技巧的关系 分层是骨架，另外三个是零件。结构化输出通常写在分层的「输出格式层」，Few-shot 写在「示例层」，CoT 写在「任务层」（要求先分析）。而 Few-shot 和 CoT 经常合体——给带推理链的示例，就是 Few-shot CoT。看到一段提示词时，先按五层切，再看每层里用了哪个零件，就不会漏。

05现实边界：不够时间、状态不好、走偏了怎么办

计划一定会遇到现实波动，这一节是给那时候看的。

缓冲在哪里

  • 每天按 3 小时排了约 2.5 小时有效任务，每天自带约半小时弹性。
  • Day 2 的代码路径是选做，整块可砍，不影响主线。
  • Day 5 的综合任务（60 分钟）是天然缓冲——前面落了进度就先拿这段时间补，补不完再砍综合任务本身。
  • Day 4 是周六，Day 5 是周日，两天都有条件临时加时。

最小可执行方案

某天只剩 45 分钟时，只做这两件事：

  • 学 30 分钟：只看当天技巧的「分辨速查」一节
  • 练 15 分钟：拆解 1 段别人的提示词，标注用了什么技巧

必须保住的三项（砍什么都别砍这三个）：Day 1 五层模板、Day 3 的 0/1/3/5-shot 对比、Day 5 拆解卡。可以舍弃的：代码 API 实操、Day 4 五题对比可减到 3 题、Day 2 可只做网页版。

检查信号与调整动作

什么时候检查看什么信号没达标怎么调整
Day 2 结束 三个任务的输出里，能被解析的少于 2 个 Day 3 开始前先花 20 分钟回到 Day 2 补一次：把 schema 写得更死（字段名加英文、加枚举、明确「不要解释文字」），补完再往下走，不要带债前进。
Day 3 结束 对比表做不出来，或看不出加几个例子开始稳定 说明测试输入太单一。换成 10 条差异更大的输入重跑，只跑 0-shot 和 3-shot 两个版本，省时间。
Day 4 结束 「该不该用 CoT」的盲测错 ≥ 3/6 Day 5 加 30 分钟重做判断练习：只练「分类该不该用」，把判断依据压缩成一句可背诵的规则。
任意连续两天 每天实际完成不到安排的一半 立刻降级：砍掉代码路径和 Day 5 综合任务，只保 Day 1、Day 3、Day 5 三天的核心动作。宁可三个技巧学扎实，不要四个都学个半吊子。
Day 5 验收 拆解卡标注准确率低于 80% 先确认是「没认出来」还是「认出来但说不清」。前者补 Day 1 分层，后者补口述练习。这周没达成就顺延两三天，不要为了赶日期放水通过。

关键假设

  • 起始日按今天 10/14（周三） 起算，到 10/18（周日）共 5 天；若你实际从别的日子开始，把日期整体平移即可，任务不变。
  • 每天按 3 小时 净投入估算（你说的是「3 小时以上」）。若实际更多，多出来的时间优先加在 Day 3 和 Day 5——这两天的样本量直接决定分辨能力。
  • 代码路径按 OpenAI 兼容 API 写。若你用其他厂商，参数名需对应调整（有的厂商只支持 JSON mode，不支持严格 schema）。
  • 「每天能投入 3 小时以上」是你自述的估计。如果工作日实际只有碎片时间，把 Day 1 / Day 3 安排在整块时间，Day 2 / Day 4 可以打散。
  • 本周目标是「能看懂和分辨」，不是做出可交付的项目。如果你中途改主意想做项目，Day 5 的综合任务就是现成的起点，但别在前四天加项目。
别踩的坑 ① 不要把五天都用来看教程——这四个知识点读两遍就懂，卡点在分辨，而分辨只能靠拆样本练出来。
② 不要在 Day 2 卡在代码环境上超过 45 分钟。装环境、调 key、查报错是时间黑洞，今天是学结构化输出的概念，不是学调 API。
③ 不要相信「加了 CoT 就一定更好」。本周最能体现你水平的一句话，是能说出「这道题不该用 CoT」。
④ 不要把模型的推理链当成它的真实想法。这个认知误区很多人带很久。
