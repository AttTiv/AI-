DAY 3 · 手把手教程

Few-shot 示例

搞懂示例到底在传达什么、给几个、怎么选、怎么排，并能一眼看出别人示例集里的坏例子。

学习 45 分钟 + 练习 90 分钟 网页版即可完成 含 4 个练习 · 附参考答案 含对比实验操作模板
今日一句话：示例不是在「教模型正确答案」，而是在「设定一个让它继续下去的模式」。 想通这一句，你再看别人写的示例，就知道它想传达什么了。

开场先看一组"看起来没毛病"的示例

这是初学者最常写出、也最没用的一类示例集。

你要做一个商品评论的情感分类器。写了这样一组示例：

# 你的提示词
判断下面评论的情感倾向，输出 正面 / 负面 / 中性。

例 1：太好用了！ → 正面
例 2：非常满意，强烈推荐！ → 正面
例 3：物流快，做工精致，五星好评 → 正面

待分类：发货慢，客服态度差，但东西本身能用。
输出：
✋ 停 30 秒

猜一下，模型大概率会输出什么？为什么？

参考答案：大概率输出「正面」——尽管这条是明显差评

为什么？模型压根没在"判断情感"。它看到的是：前面三行都是「一句话 → 正面」这个形状，于是延续这个形状，输出"正面"。

这就是今天最核心的认知：模型从示例里学的是"模式"，不是"知识"。

如果示例是在"教答案"，那模型应该知道"态度差 = 负面"——它在预训练里早就懂这个。但它输出了正面，说明驱动它的是前面三行建立的模式，跟内容对错无关。

推论：你的示例集"长什么样"，比"说了什么"更重要。三个例子全是正面，就等于告诉模型"输出正面"。这就是为什么多样性比数量重要。

把这个直觉记下来 以后写示例时，先问自己一句：我把这几个例子摆在一起，是在向模型展示一个什么"模式"？ 如果你的示例集全是一个类型，你展示的模式就是"永远输出这一类"。

01示例到底在传达什么

五个维度。你写每个示例时，都要清楚它在传达其中哪一个（或几个）。

很多人以为示例只传达"正确答案"。实际上它同时传达五样东西——这也是为什么"给几个例子"能起那么大的作用：

① 输出格式 长什么样

模型会精确模仿你示例的输出形状，包括标点、换行、字段顺序。

示例给 正面，输出就是 正面；示例给 {"label":"正面"}，输出就是 JSON。你不用额外描述格式。
② 判断粒度 多细算"负面"

这是最容易被忽略、也最需要通过示例传达的一维。纯文字描述几乎说不清。

"有点小瑕疵但整体满意"算正面还是中性？你给一个这样的例子标成"正面"，模型就知道你的标准偏宽松；标成"中性"，它就知道你很严格。
③ 标签词表 用什么词

你有自造的标签体系时，示例是唯一的传达方式。

你想让模型输出 P1紧急 / P2重要 / P3一般，光在提示词里写"按紧急程度分级"没用——模型不知道你的词表长这样。给三个例子，它立刻就懂。
④ 边界怎么判 棘手情况归哪类

混合情感、信息不足、含糊其辞——这些情况你没有示例，模型就自己瞎编规则。

"东西不错但太贵了"这种又褒又贬的，专门给一个示例标成"中性"，模型才知道你的处理惯例。
⑤ 语气与长度 输出多少字、什么调子

尤其是生成类任务（写回复、写摘要），示例长度直接决定输出长度。

你的示例回复都是 3 句话，模型就会输出 3 句话；示例是 200 字，它就不会给你 50 字。想控制长度，最直接的办法是改示例长度，而不是写"请简短"。
这个五维清单就是你的设计工具。写示例前先想清楚：我这批示例要传达的是哪几维？ 只要传达「格式」，一个例子就够；要传达「粒度 + 边界」，至少三个，而且必须覆盖不同情况。

02给几个：0 / 1 / 3 / 5 / 8 的经验值

先给结论，再用你自己的实验验证它。

数量典型增益什么时候用
0（zero-shot）—永远先试这个。摘要、翻译、改写、明显标签的分类、基于清晰上下文的问答——这些 zero-shot 就够，加例子纯属浪费
1相比 0 有明显提升只需要定格式时。风险：两个以下的例子容易被模型当成"硬规则"而不是"模式"
3相比 2 有明显提升，成本低于 5默认甜点。覆盖三类：常见情况 / 边界情况 / 棘手情况
5边际收益递减开始字段多的结构化输出、需要钉死字段顺序和嵌套结构的任务
8+通常持平甚至变差仅用于 5+ 字段的高度结构化输出，或 6+ 标签的分类（每个标签至少一个）。超过 8 个通常说明该换方法了
为什么更多不一定更好：① 例子多了会挤掉上下文里更重要的内容；② 顺序敏感性随数量增长——例子越多，换一下顺序结果越可能变。所以"多加几个保险"这个直觉是错的。

判断流程：到底该给几个

1

先写 zero-shot，拿 5 条真实输入跑一遍

如果已经能用，停在这里。Few-shot 是开销，不是装饰。

2

找出具体的失败模式

用错标签词表？漏字段？语气不对？多次运行结果不一致？每种失败对应不同类型的示例，别盲目加数量。

3

从 3 个开始，按需加减

3 个是默认起点。只传达格式 → 减到 1；字段多、结构复杂 → 加到 5。

4

A/B 对比后再决定

在同一批测试输入上比较 zero-shot 和 few-shot。如果提升不到 5%，用 zero-shot。别为了"感觉更稳"多付 token。

✋ 动手：0 / 1 / 3 / 5-shot 对比实验（90 分钟，今日主线）

这是今天最花时间也最值钱的一步。按下面的模板做，不要自己随便跑。

选一个任务：推荐客服意图分类（咨询 / 投诉 / 退款 / 建议 / 闲聊），或商品评论情感分类。选你真正会遇到的那种。

准备 10 条测试输入：覆盖常见、边界、棘手三类，故意包含几条和你的示例长得不像的。

写四个版本：0-shot（只给指令）/ 1-shot / 3-shot / 5-shot。四个版本的指令部分完全一样，只改示例部分——这样才能归因。

同一批 10 条输入，每个版本各跑一遍，记录三件事：

  • 格式一致性：10 条输出里，格式统一的占几条（有没有突然冒出"这条评论的情感是：正面"这种）
  • 判断一致性：同一条输入，重复跑 2 次，结果是否稳定
  • 加第几个例子开始稳定：从 0→1→3→5，哪一步之后正确率不再提升

重点看这两个信号：① 哪个版本之后正确率不再涨——那就是你这个任务的拐点； ② 格式一致性是不是在 0-shot 就崩了——如果是，说明真正缺的是 Day 2 的格式约束，而不是示例。

最常见的实验错误 测试输入和示例长得太像。如果你拿"很像示例"的输入去测，正确率会虚高，你会误以为模型学会了。 至少要留几条明显不像示例的输入——真正检验泛化能力的就是那几条。

03怎么选例子

选什么例子，比选几个例子影响更大。

1

多样性优先于数量

三个各不相同的例子，胜过五个长得一样的。混合容易、中等、棘手三档难度。

2

每个标签至少一个例子

分类任务里，没有示例的标签几乎永远不会被预测出来。这是硬规律，不是概率问题。

3

格式必须完全一致

所有示例用完全相同的结构、标签、分隔符、输出形状。哪怕有一个例外，模型就会开始漂移。

4

匹配真实输入分布

生产环境里 40% 是混合情感，你的示例里就该有混合情感。示例集应该是真实数据的迷你版。

5

每个例子保持简短

示例太长会烧 token 并稀释模式信号。如果你的真实输入是 200 字，示例就用 200 字，别用 2000 字。

6

标注质量比选择质量更致命

有研究明确指出：示例标错，是 few-shot 失效的最大单一因素，影响超过"例子选得不够好"。 例子少的时候（3–5 个），一个错标就能把模型带偏。加例子之前，先检查已有的例子标没标错。

一组好示例 vs 一组坏示例

✗ 坏（全同质）
太好用了！ → 正面
非常满意！ → 正面
强烈推荐！ → 正面
  • 三个都长一样，只传达了"输出正面"
  • 负面、中性标签完全没有示例 → 永远不会被预测
  • 没有边界情况示例
✓ 好（覆盖三类）
物流很快，东西也好用 → 正面
屏幕有划痕，很失望 → 负面
还行吧，没什么特别 → 中性
质量不错但价格偏高 → 中性
  • 三个标签都有示例
  • 第 4 条专门定"又褒又贬"的边界
  • 格式完全一致（同样箭头、同样标签词）

↑ 差别不在数量（3 vs 4），在于覆盖了哪些情况。

04顺序：一个被低估的变量

同样几个例子，换一下顺序，结果可能就变了。

两个已知偏差

  • 首因偏差（primacy）：靠前的例子权重更高，它们建立了初始框架
  • 近因偏差（recency）：紧贴着真实输入的那一个例子，拉力最强

不同模型偏向不同，你不需要知道你的模型偏向哪边——只需要知道顺序会改变结果这件事本身。

三种排列策略

任务类型怎么排
分类任务标签交错排列。五个正面接五个负面，会让输出偏向最后那个标签。打散成 正/负/正/负/中
格式敏感任务最有代表性的那个放最后。它锚定模型紧邻的工作上下文
高 stakes 场景至少测 3 种排序。若结果差异超过 10%，说明你有顺序敏感问题，上线前必须修
最后一个例子要特别小心：如果它恰好很短、用了罕见标签、或格式有点特殊，模型会过度放大这个特征。 检查你的示例集最后一条——它是不是你最想让模型模仿的那种？

05什么时候不该用 Few-shot

会判断"不该用"，才算真的懂了。

✓ 该用 Few-shot
  • 输出格式特殊或领域专属（你想让它照着某种内部模板输出）
  • 标签词表是自造的（P1/P2/P3、自定业务分类）
  • 需要跨几百次调用保持一致（口径不能飘）
  • zero-shot 只有 60–80 分，你要 90 分以上
  • 语气光靠描述定不住（"专业一点"说了没用，给个样板立刻见效）
✗ 不该用 / 该换招
  • 摘要、翻译、改写、润色——zero-shot 足够
  • 明显标签的分类（好/坏、是/否）
  • 大部分基于清晰上下文的问答
  • 算术、多步推理——这时候该用 CoT（Day 4），堆示例没用
  • 需要上千条例子才够的知识，或知识会持续变化——该考虑 RAG 或微调
一句话判断：你的失败是"模型不知道该长什么样"→ 用 Few-shot； 是"模型没算对"→ 用 CoT；是"模型不知道这件事"→ 该给它资料（RAG）。三种病，三种药。

06一眼看出坏例子

今日通过标准要求：能一眼指出别人示例集里的三类坏例子。下面给你四类，前三类是核心。

坏例子一：同质化 —— 几个例子长得太像
长什么样：三个示例都是同一种情况、同一个标签、差不多的长度和句式。
后果：模型只学会了这一个模式，遇到别的类型就瞎猜。这就是开场那个"全正面"的案例。
怎么修：按"常见 / 边界 / 棘手"三档各挑一条；分类任务确保每个标签至少一个。
快速检查：把你的示例集遮住标签看——如果几条输入看起来像同一个模子刻的，就是同质化。
坏例子二：格式不一致 —— 示例之间前后打架
长什么样：例 1 输出 正面，例 2 输出 这条评论是正面的，例 3 输出 {"label":"正面"}。或者分隔符一会儿用箭头一会儿用冒号。
后果：这是 few-shot 最常见的失败原因。模型看到三种格式，不知道该跟哪个，于是漂移。
怎么修：所有示例用完全相同的结构、标签、分隔符。
快速检查：把几条示例的"输出部分"单独列出来并排看——它们应该像复制粘贴出来的。
坏例子三：标错了 —— 示例本身的答案是错的
长什么样：示例里有一条明显的错误标注，比如"物流慢，很失望 → 正面"。
后果：比选错例子更致命。例子只有 3–5 个时，一个错标就能显著带偏模型，而且你很难察觉——因为格式看起来都对。
怎么修：加例子之前，先把现有例子逐条人工核对一遍。
快速检查：把每条示例的"输入"和"输出"分开，只看输出猜输入——如果对不上，就是标错了。
坏例子四（附加）：同类扎堆 —— 标签按顺序排列
长什么样：正面、正面、正面、负面、负面、负面、中性、中性。
后果：触发首因/近因偏差，输出会偏向某一类。换一下顺序结果就变。
怎么修：标签交错排列（正/负/中/正/负/中）。
快速检查：看示例集的标签序列，是不是连着三个都一样。
✋ 动手：拆解别人的示例（30 分钟，对"分辨"贡献最大）

找 3 段带示例的真实提示词（GitHub 上的 prompt 仓库、公开的智能体指令、别人分享的提示词合集都可以，中英文各来几段）。

对每个示例，标注它主要在传达五维里的哪一个（格式 / 粒度 / 词表 / 边界 / 语气）。

07限时实战（测试环节）

对应 Day 3 的测试任务：换一个没写过的任务，20 分钟内写出 3-shot 提示词。

题目

把用户反馈归类到 5 个产品模块：登录注册 / 支付下单 / 内容展示 / 消息通知 / 性能卡顿。

要求：20 分钟内写出完整的 3-shot 提示词，然后拿 10 条反馈测试。

通过线：10 条里，格式与口径一致 ≥ 8 条。

✋ 先自己写，再看参考

计时 20 分钟。写完用 10 条反馈（其中至少 3 条故意做得含糊或跨界）跑一遍，统计格式一致率。

参考写法（以及为什么这么写） 
# 任务
把用户反馈归类到指定模块。只输出模块名，不要任何解释。

# 模块词表
只能从以下五个中选一个：登录注册 / 支付下单 / 内容展示 / 消息通知 / 性能卡顿

# 示例
反馈：收不到验证码，登不进去 → 登录注册
反馈：加购之后一直加载，最后闪退了 → 性能卡顿
反馈：首页推荐的内容全是看过的 → 内容展示

# 待分类
反馈：【此处放测试输入】
输出：

为什么三个例子这么挑：

① 三个不同标签，避免同质化；

② 第 2 条（加购加载 + 闪退）跨了两个模块——它传达的是边界规则："加载慢和闪退归为性能，不归为支付"；

③ 格式完全一致：同样的"反馈：… → 模块名"结构；

④ 只给 3 个，但词表在指令里列全了——所以剩下两个标签（支付下单、消息通知）不会因为没有示例就完全不出现。

还有一处可以改进：再加一条含糊反馈的示例，比如"用起来不太顺"标成某个兜底模块，并说明"无法确定时选最贴近的一个"。这就是"边界 + 兜底"。

做这道题时注意一个现象 如果你发现 5 个模块里，有 2 个从来没被预测出来——回想第 03 节第 2 条： 没有示例的标签几乎永远不会被预测。这时要么补示例，要么像参考写法那样把词表在指令里列死并强调"只能从这五个里选"。

08怎么算学懂了

对应 Day 3 的三条通过标准，逐条自测。

今日达标清单

  • 能说清「示例 = 设模式」而不是「示例 = 教答案」。 检验方式：不看资料解释——为什么开场那组"全正面"的示例，会让模型把明显差评判成正面？答得上来就是真懂了。
  • 给出 0/1/3/5-shot 在自己任务上的对比结论。 不是背"3 个是甜点"，而是能说出：在我这个任务上，加到第几个开始稳定，为什么。
  • 能一眼指出别人示例集里的三类坏例子：同质化 / 格式不一致 / 标错了。 识别清单里至少 3 条记录，覆盖至少 2 种类型。
  • 附加：限时实战的 10 条测试里，格式与口径一致 ≥ 8 条。

最后三道检验题（闭卷）：
① 你的分类器从来不输出"中性"这个标签，最可能的原因是什么？
② 示例集里有一条标错了，和示例选得不够好，哪个后果更严重？
③ 什么情况下你不该用 Few-shot？说出两个场景。
三题都答得上来，今天就没白花。

检验题参考答案

① 最可能是示例集里根本没有"中性"的例子。没有示例的标签几乎永远不会被预测。次可能的原因是示例里中性例子放在最末尾且格式特殊，被模型放大了某种偏差。

② 标错了更严重。研究表明标注错误是 few-shot 失效的最大单一因素，影响超过"例子选得不够好"。尤其在只有 3–5 个例子时，一个错标就能显著带偏。

③ 任意两个即可：摘要、翻译、改写、润色等 zero-shot 就够的任务；明显标签的分类（好/坏、是/否）；算术或多步推理（这时该用 CoT）；需要上千条例子才够的知识（该考虑 RAG 或微调）。

今天剩下的时间怎么安排 学习 45 分钟（本教程）→ 0/1/3/5-shot 对比实验 90 分钟（今日主线，别省）→ 限时实战 30 分钟 → 拆别人的示例 30 分钟。
时间不够时优先保对比实验——你的验收标准第 2 条要靠它。对比实验可以缩减测试输入到 6 条，但四个版本都要跑，否则看不出拐点。
