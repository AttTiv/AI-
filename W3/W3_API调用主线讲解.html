W3 任务一 · API 调用主线讲解

主线：发请求 → 拿响应 → 解析 JSON → 落库 / 发通知。目标：一次看懂"程序是怎么跟外部系统对话的"。

💡 一句话先入脑：调用 API，本质上和你用上位机通过串口给一台智能传感器发"读数据"指令、传感器回你一帧数据、你拆包后记到台账或拉警报，是一模一样的事。只是"线路"换成了网络，"协议帧"换成了 URL + JSON。下面全程用这个比喻，你闭眼都能想到画面。

一、先搞懂：API 到底是什么？

API（应用程序接口）就是别人家系统开的一个"服务窗口"。你按它规定的格式问，它就按规定的格式答；你不按格式问，它不理你或报错。

硬件比喻：你车间里那台带网口的智能电表，约定"发 01 03 00 00 00 01 这帧 Modbus 指令，它就回当前电压"。这个"约定好的问法 + 回法"，就是那台电表的 API。只不过互联网上的 API 用文字（URL + JSON）而不是十六进制帧。

所以"调 API" = 按约定，向一个网址发一句话，等它回一句话。就这么简单，后面四步全是这句话的细化。

二、主线全景图（先存这张图）

怎么记：①② 是"你和设备之间的通信"（一问一答）；③④ 是"你拿到数据后在自己这边干的事"（拆包 + 处置）。前两步是"对外说话"，后两步是"对内消化"。

三、第一步：发请求（"写一张带地址的查询单"）

发请求 = 你告诉对方三件事：发给谁、用什么动作、问什么。

要素是什么硬件比喻例子
URL
（网址/接口）		对方的"窗口地址"——具体找哪个功能设备的站址 + 寄存器地址https://api.xxx.com/env/ENV-01
"查 ENV-01 这台设备"
方法
（动作）		GET=查询（我要看）
POST=提交（我塞数据给你）		读指令 vs 写指令GET 读温度；POST 上报报警
参数 / 请求体具体问什么、或提交什么内容指令里的数据域?from=2026-10-19（问哪天的数据）

一句话：发请求就像你填好一张"收件人地址 + 我要查什么"的单子，递给窗口。URL 是地址，方法是"查还是写"，参数是"查哪条"。

四、第二步：拿响应（"等回执单，先看成不成功"）

对方回你的东西分两部分：状态码（这单子成没成）+ 响应体（真正的数据，通常是 JSON）。

状态码含义硬件比喻你该咋办
200成功，数据在响应体里设备回帧、校验通过继续下一步解析
404找不到这个地址/接口站址写错，没人应答检查 URL 拼错没
500对方服务器自己炸了设备死机/内部错稍后重试，不是你的锅
超时等了很久没回音线路断了/设备没回设超时时间，失败重试

关键习惯：拿到响应第一件事先看状态码是不是 200，不是 200 就不要去解析后面的数据（后面可能是错误信息甚至空包）。这就像你收到回执先看清"成功/失败"，失败的包裹别急着拆。

五、第三步：解析 JSON（"拆快递盒，按标签取东西"）

JSON 就是互联网上通用的"带标签的数据包裹"。它用 "键": 值 的形式，让每个数据都有自己的名字，人和程序都好看懂。

给你看一个真实样子的响应（环境监测设备回的数据）：

{
  "device": "ENV-01",
  "timestamp": "2026-10-19T21:30:00",
  "readings": [
    {"sensor": "temp", "value": 25.3, "unit": "°C"},
    {"sensor": "humi", "value": 60,   "unit": "%"}
  ],
  "status": "normal"
}

逐字段拆给你看（这就是"解析"）：

片段什么意思比喻
"device": "ENV-01"这是哪台设备回的包裹上写的"发件人"
"readings": [ ... ]一个数组（方括号），里面是一组传感器一个盒子里装了多件货
{"sensor":"temp","value":25.3,...}数组里的第 1 件：温度 25.3°C盒子里第 1 个小格
"status": "normal"总状态：正常设备自诊断结论

三种"容器"记牢：
• { } 花括号 = 一个"物件"，里面是一堆 键:值（像一台设备的属性袋）
• [ ] 方括号 = 一个"列表"，里面可放多个物件/值（像一排传感器）
• "键": 值 = 标签 + 内容（像台账的"列名: 数值"）

解析这一步，就是把上面那串"文字"变成程序里能直接用的变量，比如 温度 = 数据["readings"][0]["value"] —— 翻译过来就是"取 readings 列表里第 1 个的 value"。

六、第四步：落库 / 发通知（"记台账 或 拉警报"）

数据拆出来了，总得"用"它。两条最常见去处：

去处干什么硬件比喻
落库
（存数据库）		把解析出的值写进表格/数据库，留痕、可查历史把读数记到值班台账本上
发通知
（告警/推送）		超阈值或异常时，调另一个 API 发消息（企业微信/邮件/短信）温度超标→亮报警灯 / 继电器动作

注意："发通知"本质也是一次新的 API 调用——你又去敲另一个窗口的门。所以整条主线可以"串起来"：查设备 → 解析 → 发现超标 → 再调企业微信的 API 发警报。一条主线的出口，可以是下一条主线的入口。

七、把四步连成一个完整故事

用"环境监测"走一遍，你就能在脑子里完整放电影：

  1. ① 发请求：上位机向 api.xxx.com/env/ENV-01 发一个 GET，问"ENV-01 现在啥情况"。
  2. ② 拿响应：对方回 200 + 上面那段 JSON。
  3. ③ 解析 JSON：拆出 温度=25.3°C、湿度=60%、状态=normal。
  4. ④ 落库 / 发通知：把这三个值写进数据库一行；因为状态是 normal、没超标，不发通知。如果哪天温度变成 35°C，这一步就会改走"发企业微信报警"。

这就是完整主线。你后面做 AI 项目（比如 EMC 案例库查询、器件选型接口）全是这个套路，只是"问的内容"和"存的地方"不同。

八、一段"读着玩"的示意（你不用写，看懂流程就够）

# 伪代码：把四步串起来，读得懂即可，不必会写
响应 = 发请求(方法=GET, 地址="https://api.xxx.com/env/ENV-01")

如果 响应.状态码 == 200:
    数据 = 解析JSON(响应.正文)          # 第三步
    温度 = 数据["readings"][0]["value"]
    写进数据库(数据)                    # 第四步·落库
    如果 温度 > 30:
        发企业微信("ENV-01 温度过高: " + 温度)   # 第四步·通知（又是一次API）
否则:
    记录错误("请求失败，状态码=" + 响应.状态码)  # 第二步判失败

读这段的要点：看 如果...否则 怎么对应"第二步先判 200"；看 解析JSON 之后怎么"按路径取值"；看最后的 发企业微信 怎么变成"再调一次 API"。逻辑和你写测试用例的分支一模一样。

九、新手最容易踩的 3 个坑

  • 坑1 不看状态码就解析：对方回 500 时响应体可能是错误信息，硬解析会报错。→ 先 if 200 再解析。
  • 坑2 以为 JSON 字段永远在：某天接口少回了 humi，你取 ["humi"] 就空指针。→ 取之前先判断字段存在不存在。
  • 坑3 不设超时：对方卡死，你的程序就一直干等（还记得 doc2docx 那个"卡 30 分钟"的教训吗？）。→ 请求一定带超时，超时走重试/报错。

十、验收自测（能答出＝这任务过关）

第 1 题：发请求要告诉对方哪三件事？

答：发给谁（URL）、用什么动作（GET 查 / POST 写）、问/提交什么（参数/请求体）。

第 2 题：拿到响应后，第一件该做的事是什么？为什么？

答：先看状态码是不是 200；不是 200 说明这单没成功，响应体可能是错误信，硬解析会出错。

第 3 题：JSON 里 { }、[ ]、"键":值 分别代表什么容器？

答：{ }=物件（属性袋）、[ ]=列表（多个元素）、"键":值=带标签的一项数据。
