一、背景与目标

现状：新国标大点位控制器上市后，售后端与产线端会持续回流产品问题。目前缺乏统一的登记、追踪与关闭载体，问题散落在微信群、电话、邮件与个人表格中，导致：定位靠回忆、责任难界定、对策难沉淀、同类问题重复发生。

目标：建立一套「登记 → 分析 → 对策 → 验证 → 横展 → 关闭 → 防复发」的闭环系统，做到 每条缺陷有编号、有责任人、有出口标准、有沉淀。

约束：公司办公载体为企业微信；系统需贴合现有沟通习惯，降低一线填报阻力；公司真实数据受数据主权约束。

二、总体架构原则

核心原则：状态机管「活」，工作流管「活之间的机器活」

不建议用一个巨大的工作流承载整个生命周期。原因：缺陷闭环跨人（售后/产线/研发/供应商）、跨地、常达数周，中间大量是「等人决策」；工作流引擎擅长的是确定的、机器可执行的片段。

  • 上层 = 工单状态机：定义 5 个阶段与状态；由人推动；每个状态有明确责任人 + 出口标准
  • 下层 = 事件驱动的自动化工作流：挂在每次状态转换点上，做机器能代劳的确定动作
  • AI 层 = 助理而非决策者：只做 5 件确定的事（见第七章），且不触碰责任判定
  • 知识层 = 缺陷案例库：关闭时入库，供下次检索（ROI 最高的一块）
流程框架建议：直接采用 8D + FRACAS 行业标准，不自造流程。理由：跨部门有共识基础、便于追责与体系审核、客户审厂时能直接用。
本方案五阶段与 8D 的映射：D1-D2（团队/问题描述）→ 受理登记；D3（围堵）→ 定级围堵；D4-D5（根因/永久对策）→ 根因对策；D6-D7（实施/预防再发）→ 验证横展；D8（结案）→ 关闭监控。

四、易漏环节清单（重点）

以下环节常被忽略，但恰恰决定这套系统「是摆设还是真有用」：

易漏环节为什么必须有漏掉的后果
受理即结构化源头数据质量决定后续一切分析上限一句口语描述、无批次无照片，事后无法定位，AI 也无从分析
供应商端 SCAR来料/外协问题必须追责到对方并要求其纠正内部反复整改，供应商端未动，下批照样出
设计变更 ECN改了必须有据可查、版本受控现场版本混乱，改过的问题在新批次又冒出来
认证 / 法规变更报备❓ 待确认上市后改变更或关键元器件，可能触发向认证机构报备 / 补充型式试验的义务合规级风险：可能导致证书失效、市场监管风险，远大于效率损失
标准化横展把单次经验固化进规范，并推及同系列/其他产品只修这一台，同系列其他产品原地中招
复发追踪关闭不等于结束三个月后原地复发，且无人知道曾经发生过
指标复盘Pareto / 失效率 / 外部失败成本 / 供应商评分年底汇报拍脑袋，拿不出改进依据
❓ 需你与法规/质量确认的事项：我不掌握本款「新国标大点位控制器」具体适用的新国标编号与强制性认证类别（如消防认证 / CCC / 计量器具型式批准等）。请确认：设计变更或关键元器件变更后，是否需要向认证机构报备或重做部分型式试验？ 若是，则该字段须设为强制并纳入 Phase ③ 出口标准。这条漏了是合规风险，不是流程瑕疵。

六、严重度定义与响应时限

等级定义首响时限处置要求
S 致命涉及人身安全（触电 / 火灾）；主要功能丧失且无替代方案；批量性失效24 小时内立即围堵；上报最高层并评估召回；每日跟踪
A 严重主要功能失效；导致停线或批量返工；客户强烈投诉48 小时内围堵 + 根因并行；每周复盘
B 一般部分功能异常，存在可接受替代方案5 个工作日内纳入常规排期
C 轻微外观 / 体验 / 文档类，不影响功能按需排期可合并批处理

严重度定义须在上线前与售后、生产、研发三方对齐，避免"都报紧急"导致系统失效。

七、AI 自动化节点清单

AI 在本系统中只做 5 件确定的事，每件都明确「触发时机 → 输入 → 动作 → 人工确认点」：

编号节点触发时机AI 做什么人工确认点边界
A1 结构化提取缺陷登记提交时 从口语描述+附件中抽取：型号 / 批次 / SN / 固件版本 / 现象 / 建议严重度，输出预填字段 + 置信度 必须人工确认后才可正式入库 不得自行定级
A2 相似案例检索（RAG）进入根因分析时 检索历史缺陷库 / EMC 案例库，返回 Top-N 相似案例及其根因与对策 工程师选定或否决 仅作候选，不作结论
A3 对策草稿生成根因确定后 起草 8D 报告初稿 / 围堵建议清单 必须由工程师改写并签字 不得直接对外发出
A4 知识入库缺陷关闭时 生成规范化案例摘要、自动打标签、写入向量库 质量经理确认关闭后才入库 敏感字段须脱敏后入云端版本
A5 到期催办 / 周报每日定时 扫描在办缺陷 → 超期提醒、周报汇总、Pareto 统计 无需确认（通知类） 仅通知，不得自动改状态
ROI 判断：A2（相似案例检索）价值最高——它把你现有的 EMC / 硬件经验变成可持续复利的资产，直接缩短根因定位时间，也是这套系统区别于普通工单系统的地方。建议优先投入。

八、AI 边界红线

三条不可逾越：
  1. AI 不得判定安全 / 召回级缺陷的责任结论——必须人工签字。这是对公司、对客户、也是对你自己的保护。
  2. AI 不得自动变更缺陷状态或自动关闭工单——只能提醒。
  3. AI 草稿不得直接对外（对客户 / 对供应商）——必须经责任人确认发出。

九、平台选型与落地路线

数据主权红线（优先级最高）：本系统数据是真实的公司资产，含型号 / 批次 / 供应商 / 失效率 / 成本。禁止流入扣子等第三方公共云端 AI 平台。数据应留存于企业微信 / 腾讯云生态内，或本地 / 私有化部署。第三方云端平台仅可用于练手演示，且必须使用假数据。
阶段做什么用什么产出 / 验收
Phase 0 钉死字段字典 + 8D 表单 + 严重度定义 本方案文档 + 跨部门评审会 字段字典定稿、三方对严重度定义签字
Phase 1最推荐先做 零开发跑真实数据：一个入口收单 + 一张表当库 + 人工流转 企业微信表单/收集表 ❓ + 腾讯文档 / 多维表格 连续 2 周、≥20 条真实缺陷入库；字段够用、一线愿意填
Phase 2 加轻量自动化：超期催办、周报汇总、闭环提醒 企业微信群机器人 Webhook，或本地 n8n（轻量） 催办能自动发出，超期率下降
Phase 3 上 AI 增强层：相似案例检索 + 结构化提取 + 草稿生成 本地 / 私有化 Dify + 缺陷案例向量库 A2 检索命中率可用；A1 字段预填人工修正率低
Phase 4 质量看板与指标复盘 多维表格 / BI 看板 Pareto、闭环周期、复发率可视
❓ 企微能力待确认：我不掌握贵司企业微信已开通的具体能力（是否可用自建应用、是否有「汇报/审批」高阶表单、管理员是否开放了回调权限）。Phase 1 一律按"零开发、只用表单 + 文档"规划，若具备自建应用能力，Phase 2 以后的自动化深度可再评估。请先与 IT / 企微管理员确认。

十一、风险与对策

风险表现对策
一线不愿填字段太多，售后/产线嫌麻烦，绕开系统Phase 1 只留最小必填集；其余字段由后续环节补；AI 预填降低负担
严重度通胀所有缺陷都报 S/A，失去分级意义严重度定义三方签字；由质量部复核的最终定级权
僵尸工单登记后无人推进，长期停留A5 自动催办；周会过一遍在办清单；超期计入部门考核
未接 ECN/SCAR改了但没留痕，后续追溯断链设为出口标准硬校验，不满足不得流转
认证合规风险 ❓改关键件未报备字段强制 + 法规/质量给出判定规则；上线前必须明确
数据泄露真实数据进了第三方云端见第九章红线；技术选型上一票否决

十二、下一步行动清单

  1. 本周：拿本方案与质量、售后、生产、研发四方开会，对齐严重度定义与字段必填集（Phase 0）
  2. 本周：向法规/质量确认认证变更报备规则 ❓，确定后写入表单强制校验
  3. 本周：与 IT / 企微管理员确认可用能力（表单 / 自建应用 / 回调） ❓
  4. 下周：按第五章字段字典在企微表单建表，零开发启动，跑 2 周真实数据
  5. 两周后复盘：看有多少字段没人填、多少缺陷卡在某环节，再决定是否上 Phase 2 自动化
一句话总结这份方案：这件事里 AI 不是主角，干净的字段字典 + 8D 流程纪律才是。先用零开发把真实数据跑起来，比先搭一个漂亮但没人用的系统重要十倍。
