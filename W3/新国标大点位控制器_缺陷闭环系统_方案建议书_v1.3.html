v1.3 核心修正：认证判定从「一刀切」改为「两级四档」

v1.2 把「改了固件 / 硬件」直接等同于「必须先报备、必然要送检」，判得过紧。经确认，实际规则是：

第一级：改没改只判断「是否涉及设计 / 固件 / 元器件变更」（DEF-031）。这是一个事实判断，改了就是改了
第二级：要不要报备 / 要不要送检由「变更影响判定」（DEF-034）给出四档结论：① 无需报备　② 仅需报备　③ 报备且需送检　④ 待认证机构确认。这是一个专业判断，看改了什么、改到什么程度
时序：整改与送检缺陷可以先整改、再送检。送检不再卡在整改前面；但送检样机必须与整改同步准备，不能等整改完才想起来

由此产生三处设计变更：① E 组 DEF-031 改为「是否涉及变更」（只判断事实），新增 F 组「变更影响判定」「判定依据与判定人」「送检样机准备状态」；② 阶段③ 出口标准取消「一律先备案」的一刀切硬门，改为「判定已完成即放行」；③ 阶段④ 允许「整改完成 → 送检 → 送检通过 → 关闭」的长尾路径。F 组由 5 个扩为 8 个，全表 46 → 49 个字段。

v1.1 / v1.2 已确认的事实仍然有效（本次只修正判定模型，不推翻事实）：四款型号 AEC2301 / AEC2393B / AEC2392BS / AEC2392BM；适用 GB 16808-2025；认证类别 型式试验，发证机构 沈阳消防研究所；固件 / 软件变更算关键元器件变更，另有开关电源、电池、安规电容、继电器、短路保护器件等涉及安全的元器件；先备案后实施；送检范围可选（全项 / 差异项），全项约 3 个月；证书按型号管理。
注意「固件算关键元器件变更」与本次修正不矛盾：它说明「改固件落入必须判定的范围」，不等于「改固件必然要送检」。

一、背景与适用范围

现状：新国标大点位控制器上市后，售后端与产线端会持续回流产品问题。目前缺乏统一的登记、追踪与关闭载体，问题散落在微信群、电话、邮件与个人表格中，导致：定位靠回忆、责任难界定、对策难沉淀、同类问题重复发生。

目标：建立一套「登记 → 分析 → 对策 → 验证 → 横展 → 关闭 → 防复发」的闭环系统，做到 每条缺陷有编号、有责任人、有出口标准、有沉淀。

约束：公司办公载体为企业微信；按「表单 + 文档」零开发路线；公司真实数据受数据主权约束。

二、总体架构原则

核心原则：状态机管「活」，工作流管「活之间的机器活」

不建议用一个巨大的工作流承载整个生命周期。原因：缺陷闭环跨人（售后 / 产线 / 研发 / 供应商）、跨地、常达数周（含送检则可达数月），中间大量是「等人决策」与「等外部机构」；工作流引擎擅长的是确定的、机器可执行的片段。

  • 上层 = 工单状态机：定义阶段与状态；由人推动；每个状态有明确责任人 + 出口标准
  • 下层 = 事件驱动的自动化工作流：挂在每次状态转换点上，做机器能代劳的确定动作
  • AI 层 = 助理而非决策者：只做 5 件确定的事（见第七章）
  • 知识层 = 缺陷案例库：关闭时入库，供下次检索（ROI 最高的一块）
流程框架：采用 8D + FRACAS 行业标准，不自造流程。
五阶段与 8D 的映射：D1-D2（团队 / 问题描述）→ 受理登记；D3（围堵）→ 定级围堵；D4-D5（根因 / 永久对策）→ 根因对策；D6-D7（实施 / 预防再发）→ 验证横展；D8（结案）→ 关闭监控。

四、认证变更判定模型（v1.3 重构）

一句话结论：「改了」是事实，「要不要报备 / 要不要送检」是判断，两件事必须分开问。改了不等于要报备，要报备也不等于要送检，要送检也不等于必须改完之前就送检。

4.1 第一级：改没改（事实判断，字段 DEF-031）

只回答一个问题：这次永久对策，有没有动到设计、固件、或者元器件。答「否」就直接实施、不进认证流程；答「是」强制进入第二级判定。判定范围（v1.1/v1.2 已确认，仍然有效）：

类别具体范围说明
固件 / 软件变更所有固件版本变更、软件逻辑变更★ 明确落在必须判定的范围内——但"要判定"不等于"要送检"，见 4.2
涉及安全的元器件开关电源、电池、安规电容、继电器、短路保护器件等★ 建议在表单里做成多选清单，勾选即触发第二级
其他设计变更结构、原理、PCB 等影响认证一致性的改动同样触发第二级，由质量 / 认证人员判定
这里最容易犯的错：把「固件算关键元器件变更」直接读成「改固件必须送检」。前者说的是落入判定范围，后者是判定结论。差一步，就会让所有固件小改动都被塞进 3 个月的送检队列，系统也就没人愿意用了。

4.2 第二级：变更影响判定（专业判断，字段 DEF-034，四档）

由质量 + 认证对接人给出四档结论之一，并把依据写进 DEF-035（改了哪些内容 + 依据什么判成这个结论 + 双签）。四档走向完全不同：

判定结果报备送检流程（关键节点顺序）
① 无需报备否否整改 → 内部验证 → 关闭。最快路径，不碰认证
② 仅需报备是否备案 → 拿回执 → 整改 → 内部验证 → 关闭
③ 报备且需送检是是备案 → 整改与样机准备并行 → 内部验证 → 寄样送检（全项约 3 个月）→ 送检通过 → 关闭
④ 待认证机构确认待定待定只允许先做围堵 + 临时对策（不动认证相关设计）；永久变更暂缓，等答复后落②或③

为什么必须有 DEF-035「判定依据与判定人」

四档判定本质是专业裁量，同一处改动，不同人可能给出不同结论。系统不能只留一个「③」的标签，必须留下为什么是③：

  • 对内：半年后回头看，只有依据能解释当时的判断，否则无法复盘、无法追责
  • 对外：认证复查、客户审核、监管问询时，这一段就是最直接的合规证据
  • 对下批：同一个型号再来一次类似变更时，这段依据直接变成判定先例，判定速度会越来越快

红线不变：AI 不得代做这一档判定（见第八章第 4 条），只能提示"历史上类似变更被判为②/③"。

便于一线理解的举例方向（非规则，仅供理解）：动到型式试验所覆盖特性的改动——如报警响应时序、点位容量、通信协议一致性、电源适应性、绝缘耐压相关设计——通常往③靠；只动外观丝印、包装、非安全相关说明书措辞，通常落①或②。具体边界尚未与沈阳消防研究所逐条确认，一律按人工判定执行（见附录 ❓A1）。

4.3 时序：整改和送检，谁先谁后（v1.3 的核心修正）

v1.2 的错误假设：把「送检」写成了整改之前的硬门，等于要求先送检、后改缺陷。这在工程上不成立——没改好拿什么送检。

正确的时序是两条线并行、三个节点收口。判为③的缺陷，时间线长这样：

节点事件谁负责要点
T0判定 = ③，当天启动送检样机准备质量（认证对接）★ 不是整改完才启动。DEF-038 当天从「未启动」变「备料中」
T1备案回执到手，允许实施永久对策质量 / 认证对接「先备案后实施」仅作用于报备，与送检时序无关
T2整改完成 + 内部验证通过研发 / 测试到此为「技术闭环」——缺陷本身已经修好了
T3a样机方案锁定：来源、数量、状态一致性三项定下来并存档质量 / 认证对接★ 硬判据：T3a ≤ T2，且实际应在 T0 之后几天内完成。方案不定，后面全是空转
T3b样机物理齐套（走完 ECN 的正式状态，可装箱寄出）质量 / 生产★ 判据分两种情形：改固件的应 T3b ≤ T2；换料 / 改硬件的必然 T3b > T2，此时看的是"晚了多少"，晚的部分应只剩新料的最短周期
T4寄样送检，进入「等待送检（外部）」质量全项约 3 个月，属外部不可控周期
T5送检结论 = 通过，方可关闭质量不通过 → 打回阶段③重做对策，不是重开新单

为什么 T3 要拆成 T3a / T3b —— 「T3 ≤ T2」不能一刀切

初稿把判据写成「样机齐套日期 ≤ 整改完成日期」，这条只在改固件时天然成立：硬件样机现在就能备，整改完刷入新固件即可寄出，两件事完全可并行。
但若整改是换料 / 改硬件，样机必须用新料，新料要等 ECN 走完、采购到货、试制完成——T3b 在物理上不可能早于 T2。这时还拿「T3 ≤ T2」去考核，等于考核一件做不到的事，考核就废了。

整改类型样机能否与整改并行该用哪条判据
改固件 / 改软件能。硬件用现有版本先备，整改完刷入新固件T3b ≤ T2 必须做到；做不到就是准备启动晚了
换料 / 改硬件不能完全并行。样机必须用新料看 T3b − T2 的差值：应只剩新料最短周期（采购 + 试制），不许多出"忘了启动"的时间。T3a ≤ T2 仍必须做到
改工艺 / 改检验 / 更新文件不涉及样机状态本判据不适用；只看送检范围是否受影响

一组数字看懂差距（3 月 1 日判定=③，整改 + 内部验证 45 天 → T2 = 4 月 15 日；备样机需 30 天）：

做法样机启动样机齐套 T3b实际寄样时间
等整改完才启动4/15（= T2）5/155/15 —— 整改完成后白等 30 天
T0 当天启动3/13/314/15 —— 整改验证一过当天即可寄样，省 30 天

两种做法的整改速度一模一样，闭环总时长差整整一个月。这一个月既不来自研发加急，也不来自机构催办，纯粹来自"什么时候开始备样机"。

这次修正带来的两个直接效果：
  1. 缺陷不再被送检堵住。研发该改就改，整改周期不被 3 个月的外部周期绑架；内部验证通过即算技术闭环，客户侧可以先靠围堵措施应对。
  2. 但样机准备被顶到最前面。既然送检排到了整改之后，那"前面省下的时间"必须用来备样机——否则就是把等待从前面挪到后面，总时长一点没省。

4.4 送检样机提前准备，具体要定哪三件事

要定什么说明
① 样机来源工程样机 / 量产抽样 / 库存机三选一，写进 DEF-038 备注。来源决定备料路径长短：量产抽样要等排产窗口，工程样机要排试制
② 数量型式试验有抽样台数要求，数量未定就没法备料。❓ 具体台数需按 GB 16808-2025 与沈阳消防研究所要求确认（附录 ❓A2）
③ 状态一致性★ 必须是走完 ECN 的正式状态，不能是工程师手改、飞线、临时改料板。手改板送检 = 检的不是要生产的东西，结论无效且白花钱
这是全流程最容易被忽视的一处：整改完成、内部验证全过、大家都以为快结束了，结果发现手里没有一台合规状态的样机——要么是手改的，要么固件版本对不上，要么数量不够。于是从零开始备料排产，前面省的时间全还回去，还可能连带错过交付节点。
对策分两层：① T0 当天锁定方案（T3a ≤ T2），这一步没有任何物理障碍，纯靠流程；② 物理齐套按整改类型分判——改固件的用「T3b ≤ T2」硬卡，换料的把 T3b 压到只剩新料最短周期。

4.5 对状态机与 KPI 口径的连带修正

v1.2 因为假设「送检阻塞整改」，把整个等待期都算成外部时间。修正后需同步改三处，否则 KPI 会变得比修正前更失真：

项目v1.2 口径v1.3 修正
「等待送检（外部）」起点判定为③即进入整改完成 + 内部验证通过后才进入。整改期间仍是「对策中 / 验证中」
内部时长是否豁免等待期整体豁免不豁免整改期——判为③的缺陷，整改慢照样算内部超期。送检只豁免外部等待段
催办时点按「预计送检完成日」提醒新增一条：判定=③当天生成「样机准备」待办，并在 T2 前 15 天检查 T3a 是否已锁定、T3b 是否已齐套（按整改类型判）

八、AI 边界红线

四条不可逾越：
  1. AI 不得判定安全 / 召回级缺陷的责任结论——必须人工签字
  2. AI 不得自动变更缺陷状态或自动关闭工单——只能提醒
  3. AI 草稿不得直接对外（对客户 / 对供应商）——必须经责任人确认发出
  4. AI 不得判定「变更影响」（四档结论）——GB 16808-2025 型式试验（沈阳消防研究所）下的报备 / 送检判定，必须由质量 + 认证对接人人工完成并双签；AI 只能返回历史同类变更的判定先例与依据（v1.3 表述修正：从「不得判定是否报备」扩为「不得判定四档」）

A5判定为③（或②）后，若整改方案在实施中发生变化（比备案时改得更多 / 更少 / 换了项），是否需要补充或重新备案是否重新判定内部已定（一定重新判定，见下方说明）；但对外是否需补充备案，取决于机构的受理规则，不是我们能单方面定的。建议问法：「备案提交后，若实际实施的设计变更范围与备案内容不一致（扩大、缩小或换项），是否需重新提交备案？是否存在幅度阈值？」
关于 A5 为什么必须问机构，而不是自己定一条规则：
  1. 备案是对外行为，有效性由受理方认定。内部流程管得住我们自己，管不住机构认不认。自己定"改一点不用补备案"，出了事责任在公司，不在流程文件。
  2. 超出备案范围，性质就变了。举例：判②按"改 A"备案并拿到回执，实施中发现光改 A 不够、得连 B 一起改，而 B 也在型式试验覆盖范围内。此时已超出备案范围，机构可能认定实际做的是未备案变更，原回执对 B 无效。注意"少改"一般不算新变更，"多改 / 换项"才是风险点。
  3. 这类细节不会写进公开文件。法规写"变更需备案"，但"幅度多大算新变更、缩小要不要补报"属于受理时的操作惯例，只能直接问对接人。
所以按两层执行，不要混：
内部（已定）整改方案只要变化，一律重新判定；DEF-034 允许被改写但保留历次版本与依据，不得覆盖
对外（待确认）是否需补充备案，按机构答复执行。这样即使答复慢，内部判定也不会失控
