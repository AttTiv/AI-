一句话说清这份教程的定位：扣子负责让你「今天就把知识库跑起来、看到端到端效果」； 它不负责让你看清切分与排序的细节 —— 那部分由本地的 mini_rag.py 补。 两个工具分工，不是二选一。

一、为什么是扣子，不是 Dify

计划文件 W4-③ 原文写的是「用 Dify 或 LlamaIndex 搭第一个知识库」。那行是举例，不是限定。 真要在你机器上落地，三个选项的实况是这样：

工具起步门槛你能看到什么结论
Dify Docker 全栈，运行要吃 4–6 GB 内存 全流程、可改代码、可换模型 你装不了。本机总内存 13.8 G、实测空闲仅 2.5 G，Docker 与 Ollama 均未安装
LlamaIndex 要写 Python 一切，因为全是你的代码 和你的约束冲突。你不学写、只学读，时间会全耗在调环境上
扣子 浏览器登录即可，免费版 1 GB 知识库空间 分段结果、召回测试、Score 分数、检索策略开关 选它云端跑，不吃本机内存；W3 你已跑通过扣子工作流，账号现成
一条必须讲清的代价：扣子是闭源平台，你的文档会上传到它的服务器。 所以这份教程用的是你自己写的设计文档 + 公开资讯，不含真实缺陷记录、客户信息、报价。 型号（AEC2301 等）算不算敏感，你自己拍——要更保险，上传前把型号替换成代号即可。

看图就懂为什么两个工具要分工：扣子把「看得见」的三步做得非常好用（分段能改、能抽样、能测召回）， 把「看不见」的三步封装得干干净净。你要学的是这三步为什么这么设计，那就得回本地脚本。

1登录，进资源库

浏览器打开 coze.cn，用 W3 那个账号登录 → 左侧栏「资源库」→ 右上角「+ 资源」→ 选「知识库」。 类型选文本格式（另有表格、图片两类，这次用不上）。

2分段设置：一定要选「自定义」

新建时会让你选分段方式，两个选项差别巨大：

选项平台怎么切建议
自动分段与清洗平台按预置规则切，你无法干预不要用了你什么都学不到
自定义你指定分隔符 + 最大分段长度（100–2000 字符）+ 是否过滤连续空格/URL 邮箱选这个

具体这样填：

分段标识符：  换行符（先用默认；你的文档标题层级明显，也可以填 ## 或 第 X 章 试）
最大分段长度：500 字符
过滤连续空格/换行/制表符：开
过滤所有 URL 和邮箱：开
为什么是 500？
不是抄来的，是你在本地 mini_rag 里实测过的那一档（200 / 500 / 1000 三档对比，500 的解释最完整）。 两边都用 500，差异才可比 —— 这是做实验的基本要求：一次只改一个变量。 注意单位是「字符」不是 token。中文里 500 字符 ≈ 330～500 token，跟本地脚本的 500 字基本同量级。

3上传 16 份，等解析

把 corpus_pdf 里 16 个 PDF 全选拖进去。单批上传会更稳，失败的文件会在列表里标红，重传即可。

等状态从「处理中」变「已完成」。这一步平台在做：抽文本 → 按你的规则切段 → 逐段算向量 → 入库。

4抽样检查分段质量（这一步别跳）

点进知识库，看「分段」列表。随机点开 5 段，逐条看三件事：

  1. 中文是不是正常（有没有变成乱码或一串问号）
  2. 有没有半句话被切断（比如「T3 ≤ T2」后面直接没了 —— 这正是本地脚本踩过的坑②）
  3. 一段里是不是只讲一件事（混了三件事说明 500 太大，混不到一件事说明太小）
PDF 的已知副作用：从 PDF 抽文本时，某些排版会在汉字之间插入空格（「围 堵 措 施」）。 如果你看到大量这种，字面匹配会变差（这也是为什么平台默认用「混合检索」而不是纯字面）。 这是 PDF 转换的代价，不是平台的问题 —— 想彻底避开，得改用 docx 或 md 上传。

5建一个 Bot，把知识库挂上去

左侧「工作空间 / 项目开发」新建一个智能体，名字随意（比如「闭环系统问答」）。 在编排页左侧找「知识库」→ 点「+」→ 选中刚建的知识库。

6召回设置：这是全篇最关键的四个开关

设置项本次填什么为什么
调用方式自动调用按需调用要你在提示词里写「什么情况查哪个库」，第一次用别自找麻烦
搜索策略先选混合混合 = 全文检索（关键词）+ 语义检索，两路一起排。专有名词靠字面、同义词靠语义，本地脚本缺的就是这一路
最大召回数量3（先按默认）取太多噪声进 prompt，先固定 3，第五节的实验中再改
最小匹配度0.55 起（可调范围 0.01–0.99）低于这个分数的段不返回。设太高会「什么都搜不到」，设太低会「什么都往里塞」

另外把「显示来源」打开 —— 你需要看到它到底引了哪一段；「无召回回复」设成「资料中未提及」。

7跑三道题，看它捞对没有

直接用 W4 那三道题。每题问完，点开引用来源，把命中段和分数抄进第五节的表。

Q1　临时围堵措施由谁在什么时候做？
Q2　主表建了几列，47 个字段里必填几个？
Q3　样机判据是「T3 ≤ T2」吗？

8做一次「引文作答」对照

在 Bot 的提示词里加一条硬规矩，然后再问同样三题：

回答规则：
1. 先逐字引用你检索到的原文段落（用 [1][2] 标号），再给结论。
2. 引用的段落里没有的信息，一律回答「资料中未提及」，禁止补充。
3. 如果不同段落说法冲突，把两种说法都列出来，指出各自来自哪个文件。

第 3 条是给你埋的 —— 因为语料里同时存在 v1.2 和 v1.4 两份方案书，只要它老实列冲突，就说明这条规矩生效了。

做不到后果补位方案

七、五个坑（扣子版）

坑现象怎么修
① 直接传 html提示格式不支持 / 解析出空白先转 PDF（我已在 corpus_pdf 转好），或另存为 docx
② 把「字符」当「token」设 500 以为跟本地一样，实际段数对不上500 字符 ≈ 330～500 token，比本地 500 字略短。对比时看段数，不看设定值
③ 阈值设太高「资料中未提及」连发，什么都搜不到一个跨多个知识点的问题，匹配度可能只有 0.3–0.6。降到 0.3 试，或把召回数量加到 5
④ 旧版本混进去
故意埋的		它引用 v1.2 的旧口径，理直气壮地答错这就是真实世界的常态。修法不是删文件，是让它报冲突（第三张表要测的）
⑤ PDF 抽取夹空格分段里出现「围 堵 措 施」，字面匹配变差优先用「混合检索」；长期解法是改用 docx / md 上传
第 ④ 条要专门说一句：你会在召回结果里看到 v1.2 和 v1.4 同时被命中，而且旧版可能分数更高（写得更啰嗦）。 这不是 bug，是 RAG 的本性 —— 它不知道哪份是现行版本。 真实工程里的解法是给文档打「版本/状态」元数据，检索时只查现行版。 你现在能做的：只上传现行版建第二个库，和混合库对比一次，把差异写进表 1。
