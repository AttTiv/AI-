一、一句话说透 RAG

RAG 不是给模型加知识，是给它一份参考资料，让它开卷考试。

你现在用的模型，脑子里装的是全人类的公开语料，它不知道你公司的样机判据怎么定、不知道你主表为什么是 20 列。 你想让它在你的文档上答题，有两条路：

路子做法代价
微调（不改这周学）把你的文档喂进去重新训练一遍参数贵、慢、改一次要重训；而且模型会「记混」——它把文档压缩进参数，细节就丢了，还会一本正经地编
RAG（本周学）文档不动，每次提问时先把相关段落查出来，连同问题一起塞给模型文档随时改、随时生效；答案能标注出处；查不到就说查不到
记住这一句就够本课了：RAG 里模型没变聪明，变的是它答题时手边多了几页复印件。 所以答案准不准，八成取决于「那几页复印件找得对不对」，不到两成取决于模型本身。 这也是为什么 W5 要花一整周去优化「召回率」—— 找错了页，模型再强也只能照着错页答。

二、五个环节长什么样

图 1 · RAG 六个环节。上半截建库只做一次，下半截每次提问都跑一遍

用你熟的场景翻译一遍

环节RAG 里的动作硬件语境里的对应物
1语料把你的一堆文档收进来、转成纯文字把方案书、作业单、台账统统摊在桌上 —— 注意 PDF 扫描件要先 OCR，这一步最容易出脏数据
2切分长文档切成一小块一小块把整本说明书拆成一页页 SSOP 工位卡：一张卡只说一件事，工人拿起来就能干活。切太碎则一句话没说完就断，切太大则一张卡混了三件事
3向量化每块算出一组数字（向量）给每张卡打特性指纹，像器件丝印编码：同型号的指纹挨得近。这一步之后，"围堵"和"止血"即使字不同，指纹也可能很近
4存库把指纹和原文一起存进数据库带坐标索引的物料柜：抽屉按指纹相似度排，抽哪一格不用翻全柜
5检索问题也算成指纹，找最像的 K 块拿故障现象去柜子里抽 3 张卡，不是把整个柜子倒出来
6生成3 块原文 + 问题一起给模型把 3 张卡的复印件夹在工单后面交给工程师：照卡答，不许凭记忆
一个数字先记住：你这份语料切完是 114 块，检索只取 3 块。 也就是说，模型每次只看到全部资料的 约 2.9%（3×463÷47598 = 1,389/47,598）。 剩下 97.1% 它一辈子也看不到。这就是 RAG 全部威力和全部风险的来源 —— 找对了是神力，找错了是灾难。

三、为什么这一课不装 Dify

计划文件里 W4 任务三写的是"用 Dify 或 LlamaIndex 搭第一个知识库"。我建议这一课先不装，理由是实测数据：

项目实测值结论
本机总内存13.8 GB—
当前空闲内存2.5 GBDify 全栈（约 15 个容器）要 4–6 GB，现在装必然吃 swap
Docker未安装装 Docker Desktop 本身再吃 1–2 GB
Ollama（本地模型）未安装7B 量化模型要 5 GB 以上，更不可能
所以本周的路线：先看清，再上工具。
用本地 Python 脚本 + 你已有的 DeepSeek key 跑通五环节 —— 内存只要几十 MB，全程看得见每一步的输入输出。 等你亲手见过"切分—索引—检索"长什么样，再去 Dify 里点按钮，才知道那些按钮在替你干什么。 反过来先学 Dify，你会变成"会拖节点但不知道节点在干嘛"的人——这正是招聘里说的"vibe coding 但不懂架构"。

Dify 什么时候上：W5 建评测集的时候。那时你需要频繁改配置、跑批量对比，界面的效率才划算。届时先关掉一半浏览器标签把内存清到 6 GB 以上。

三道题（答案只在上面这堆文档里，你熟，能秒判对错）

Q1 · 跨文档对照　「紧急围堵措施」和「围堵措施（临时）」，分别是哪个阶段填、谁填、什么时候填？
答案紧急围堵 = 质量部，受理当天就做，S/A 级才触发（C 组"定级与围堵"字段）；围堵措施（临时）= 研发，根因分析之后做（E 组"对策"字段）。两者信息前提不同，前后差 3~5 个工作日，所以不能合并。出处：依赖图 第五节「五个最容易填错的地方」第 4 条 / 方案书 v1.4 第三节「② 定级围堵」
Q2 · 数字对账　主表建了几列？47 个字段里必填几个？还有多少列延后？
答案主表 20 列 = 用到其中 16 个字段 + 4 个系统/状态列（创建人、最后更新时间、当前状态、当前责任人）；47 个字段里必填 10 个。延后数量见下方冲突提示。
Q3 · 判据防误导　样机判据是不是「T3 ≤ T2」？
答案不是，不能一刀切。要拆成 T3a（方案锁定，必然 ≤ T2）和 T3b（物理齐套：改固件应 ≤ T2，换料必然 > T2）。拿"T3 ≤ T2"去考核等于考核一件物理上做不到的事。出处：方案书 v1.4 第二节「为什么 T3 要拆成 T3a / T3b」/ 交接卡「已经定死、不要重新讨论的决策」里的"样机判据"那一条
Q2 里我埋了一个真实的坑，你自己核一下。
建表作业单 v2 原文写「主表 20 列 = 用到其中 16 个字段 + 4 个系统/状态列……其余 32 个字段延后」。
但算一遍：47 − 16 = 31。差 1。 ❓
两种可能：① "32" 是笔误，应为 31；② 口径里把某个系统列也算成了一个待建字段。 这个我不替你定 —— 你确认后我改文档。这也正好是本周的活教材：RAG 会把文档里原有的错误，原样放大成"权威答案"。

七、答错了到底是谁的错

计划文件 W4 第五条要求你分清"没检索到"和"检索到了没用上"。这两种病治法完全相反，判断方法只有一步：先看检索结果里有没有正确答案。

图 2 · 先判病再开药。搞反了就会陷入"疯狂改 prompt 但检索一直是错的"的死循环
脚本里已经给你留了这个钩子。第 4 段会把每一块的原文打出来 —— 不要只看最终答案，先看那 3 段原文。 养成这个习惯，你排查 RAG 问题的速度会比别人快一个数量级。

再往下拆：这两种病，其实各有三种

上面那棵树只分了两支，够你判断方向，但不够你开药。工程上真正要区分的是六个具体故障点。这个分类不是我编的 —— 来自 Barnett 等人 2024 年的经验报告《Seven Failure Points When Engineering a RAG System》（CAIN 2024），基于三个真实案例（论文审阅、38 篇文档的教学助手、4,017 篇文献的生物医学问答）。它最有价值的一句话是：七个故障点里，有三个发生在模型看到任何内容之前，四个发生在看到之后。

第一类 · 没检索到（模型根本没看见）

具体故障说人话典型原因解法（按性价比排）
① 语料里本来就没有
最常被跳过		 不是检索没找到，是库里从来没这本书。模型却会编一个听起来合理的答案，而不是说"不知道" 新流程还没写进文档；文档只写到 v1.3，你在问 v1.4 才有的口径 补语料是唯一解。检索算法再改也救不了；同时在 prompt 里硬性要求"资料没有就说没有"
② 有，但没排进前 k 书在架上，管理员也翻到了，但没放进"给模型的那三本"里 只用字面匹配，问法和原文用词不同（"怎么止血" vs "围堵"）；专有名词被泛词淹没 混合检索（BM25 + 向量）→ rerank 重排 → 查询改写 → 最后才是加大 k。你 Q1 的 Top-1 是无关 CSV 行、正确答案排第 2，就是这一类
③ 排进了，但被挤掉 管理员抱来 20 本，桌子只放得下 5 本，剪裁时把最要紧那本丢了 召回数设得很大（k=20），拼 prompt 时按 token 上限截断，截掉的正好是答案 召回多、喂给模型少：用 rerank 从 20 里挑 3~5。或改用父块回填（小块检索、整节喂进去）

第二类 · 检索到了但没用上（模型看见了，没使上）

具体故障说人话典型原因解法（按性价比排）
④ 被噪声或矛盾搞混
你语料的高危项		 答案就在眼前，可旁边还堆着十段无关内容，或者两段互相打架，模型挑了个错的 Top-k 里混进大量沾边不相关的块；同一件事有新旧两个版本共存 降 k + rerank 提纯；给块打版本元数据，检索时只取现行版；prompt 硬性要求"说法不一致就并列两种并指出冲突"
⑤ 位置太靠中间 一本书摊开，人眼总先看开头和结尾，中间那段最容易走神。模型也是这样 上下文太长，答案落在中段 最相关的放首尾；指令放开头和结尾各一遍；根本解还是减少块数
⑥ 只答了一半 问"这三份文档各写了什么"，只答了两份，第三份明明在上下文里 一个提问里塞了多个子问题；输出太长时后段被压缩 拆成子问题分别问；prompt 里列清单式要求（"逐份回答，不得遗漏"）
这两条有实测数字支撑，不是我推的。
刘等人《Lost in the Middle》（TACL 2024）做过一个很直接的实验：给模型 20 篇文档，答案只在一篇里，然后只改这篇的位置。结果是一条 U 型曲线 —— 放开头和结尾答得最好，放中间时 GPT-3.5-Turbo 的准确率甚至低于不给任何文档的 56.1%。
更值得记的一个数：把召回从 20 篇加到 50 篇，GPT-3.5-Turbo 只提升约 1.5%，Claude-1.3 约 1%。也就是说"多给几块"几乎没用，这是反直觉但被反复验证的。

为什么这两种病的治法正好相反

你的动作对「没检索到」对「检索到了没用上」
加大 top-k有帮助，能兜住排在后面的正确块有害，噪声变多，正确块被稀释、被推到中段
把文档切得更细有帮助，命中更准有害，块更碎，结论容易被切断
加 rerank 重排有帮助有帮助 —— 唯一两边都受益的动作
改 prompt几乎无用，内容压根没进来有效，尤其"先引用再作答"
这就是为什么必须先分诊。Barnett 那篇的原话意思是：只调 prompt 的团队，只在七个故障点里的四个上工作，另外三个碰都碰不到 —— 而检索和切块恰恰是错误最集中的地方。
落到你身上：如果 Top-3 原文里没有那句答案，改 prompt 改到天亮也没用。

怎么验证：两个指标，必须分开测

这两种病不能合成一个"准确率"看，否则永远不知道往哪修。RAGAS 这套评测框架的做法是拆成四个指标，其中两个正好对应你这两个病：

指标问的是什么对应哪种病
上下文召回
context recall		标准答案里的每个要点，在检索出来的块里找得到吗没检索到（①②③）
上下文精度
context precision		检索出来的块里，有几块真的有用；正确块排第几没检索到（②③）
忠实度
faithfulness		答案的每一句，能在给出的块里找到依据吗检索到了没用上（④⑤⑥）
答案相关性

好消息是前两个可以零成本手算：你手上有标准答案，只要把正确那块在第几名找出来，召回和排名就都有了 —— 不需要再调一次模型。这也正是 W5 建评测集的起点：先能测，才谈得上优化。

让模型"先引用再作答"

九、能不能做多层 RAG（11-04 追加）

原提问：素材很大时（例如《PMBOK 指南》17 万字），是不是可以做一级 RAG、二级 RAG、三级 RAG 这样往下叠，就能把内容检索得更充分？

结论：方向半对，做法反了。
「分层检索」是真的、也真的在用（有正式名字），但你设想的「一级筛完给二级、二级筛完给三级」恰好是论文里被否掉的那种走法； 而且 17 万字远不到需要它的量级。你现在的问题不是「层不够多」，是「第一层就常排错」。

先承认：这门技术存在，只是不叫「一级二级三级」

正式名字它怎么分层什么时候用
父子文档检索
parent-child / small-to-big		小块拿去检索，命中后把它的父块（整节）喂给模型生产上最常用。这正是「两层」的正确形态：细找、粗给
RAPTOR
递归摘要树		把块聚类 → 让模型写摘要 → 摘要再聚类再摘要，形成多层树问题需要全局综合时（"这本书主线是什么"），单层检索根本答不出
查询路由
routing		先判断该查哪一章 / 哪张表，再进那一块里检索语料有清晰目录结构时，最便宜的一层

注意共同点：这三个的分层都是用来「改变粒度」的，没有一个用来「逐级淘汰」。

为什么「逐级往下筛」会亏

不用讲概率，一条逻辑就够：第二级只能在第一级交上来的候选里挑。第一级没留住的那块，后面永远拿不回来。 所以串联结构里，最终召回率的上限被第一级锁死，叠得越多，能答对的机会只会更少、不会更多。

如果每级各自有 90% 的把握留住正确答案，串起来是这样：

每级留住正确答案串 2 级串 3 级串 4 级
95%90%86%81%
90%81%73%66%
80%64%51%41%

真实系统里各级并非彼此独立（第一级给的范围越大，后面越容易救回来），实际衰减比这张表缓一些。 但方向不会变：每多一级，就多一个「必须对」的关口。

RAPTOR 原论文自己做过这两种走法的对比，结论对你不利：
· Tree Traversal（逐层下降）：从根往下，每层只进选中节点的子树 —— 一旦顶层摘要和问题措辞对不上（词汇不匹配）或摘要过度抽象，整棵子树就被永久排除。
· Collapsed Tree（压平）：把叶块和各级摘要倒进同一个池子，一次相似度打分，跨层取前 k —— 论文实测一致优于逐层下降。
换句话说：树可以建，但检索时不能顺着树往下爬，要横着捞。

那 17 万字到底要不要分层

先算三个数结果
17 万字大概多少 token按你 7 份文档实测的 0.67 token/字折算 ≈ 11.4 万 token。豆包 25.6 万窗口塞得下
切成 500 字一块是多少块约 340 块
取 Top-5 喂给模型是多少2500 字 ≈ 全文的 1.5%

所以 17 万字的真正难点不是「装不下」，是「怎么让对的 5 块排进前 5」。这件事跟层数无关，跟排序质量有关。

判断口诀：问「在哪」用一层，问「整体」才要树。
· PMBOK 的题九成是「某过程的输入输出是什么」「变更要走哪几步」—— 定位型，一层足够，叠层只有坏处。
· 只有「十个知识领域之间怎么耦合」「这本书的管理思想怎么演变」这类全局综合题，单层真的捞不到，那时树才有意义。
按这个标准，你手上「缺陷闭环系统」的提问 95% 是定位型（某字段谁填、某状态能不能跳）。你不需要树。

想提精度，按这个顺序做（性价比从高到低）

手段怎么做为什么排这个位置
① 结构过滤
（元数据）		先按章节 / 阶段把范围缩到一章，再在章内检索成本接近零。PMBOK 的目录、你文档的 8 阶段 47 字段，本身就是现成的过滤器。这一层不叫 RAG，叫「先别乱找」
② 混合检索BM25（字面）+ 向量（语义）两路并取专有名词（SCAR、ECN、T3b）靠 BM25 才稳；同义词靠向量。第 8 节那个「来料/开单」翻车，就是只有字面这一路
③ rerank 重排先取前 50 块，再用重排模型挑出前 5提升最大的一步。你现在 Top-1 常是垃圾、正确块排第 2，就是缺这一下
④ 父块回填小块检索，命中后把整节喂进去解决「块切断了结论」（第 8 节坑②）。这才是两层：不是筛两次，是细找粗给

真要建树，记住两条

一、检索时压平，不要往下爬（上面 RAPTOR 那段）。二、先算代价： 建树要在入库阶段额外让模型写摘要，约多花 0.3～0.5 倍语料的 token；索引规模膨胀到 1.3～1.5 倍；文档一改，上层摘要就失效。 （数字来自 RAPTOR 论文及其工程解读，不同来源口径略有差异，量级可信、精确值别当定论 ❓）

最后一条对你最致命：你的方案书还在 v1.3 → v1.4.2 迭代，字段口径还在改 —— 每改一次就要重建上层摘要。 树适合稳定的语料，不适合天天改的活文档。你现在这套文档，恰恰是后者。

一句话带走：多层 RAG 不是「检索得更充分」，是「用不同粒度回答不同层级的问题」。
你现在缺的是排序精度，不是层级数量。所以 W5 该做的是评测集 + rerank，不是往上叠层。
来源：RAPTOR 原论文（Sarthi 等，ICLR 2024）及两篇工程解读；「压平优于逐层下降」为论文结论，「召回提升 20%–35%、索引膨胀 1.3–1.5 倍」为二手汇总口径。

四个问题，都能在代码里指出位置才算过。不需要会写，只需要能指出。

问题标准答案
① 它读哪些文件？配置区 24–32 行 的 CORPUS 列表，7 个文件名，都拼在 BASE 目录下
② 切成什么？chunk_docs（72–93 行）：按段落切 → 累加到 ≤500 字 → 相邻块重叠 50 字
③ 存到哪？_out/index.json，里面是 {chunk_size, chunks[{id,src,text}], idf_top}。打开看一遍
④ 怎么查出来？search（137–150 行）：问题同样切词 → TF-IDF 权重 → 与每块算余弦 → 排序取前 K
加一道更硬的（能答出这题，说明你真读懂了）：
「想换用真 embedding，要改哪几行？为什么其余部分不用动？」
答：改第 3 段的 build_index（114–132）和第 4 段的 search（137–150），把"双字切片 + TF-IDF"换成"调 embedding 接口拿到向量 + 算余弦"。 其余四段不用动 —— 因为切分、存储、拼 prompt 这三件事跟用什么算法算向量完全无关。 这个"接口不变、内部可换"的分层，就是你能看懂任何 RAG 框架（LlamaIndex / Dify）的底层原因。
